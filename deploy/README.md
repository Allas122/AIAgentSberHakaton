# Деплой

## Как устроено

Два раздельных workflow:

| Workflow | Триггер | Что делает |
|---|---|---|
| `.github/workflows/build.yml` | push в `main` + кнопка | Собирает 3 образа на раннере GitHub и пушит в GHCR |
| `.github/workflows/deploy.yml` | **только кнопка** Run workflow | Заходит по SSH на VPS, снимает дамп БД, подтягивает образы, перезапускает |

Сборка отделена от выката намеренно: каждый push в `main` готовит образы, но на прод ничего не попадает, пока не нажата кнопка.

`remote-deploy.sh` **копируется на сервер и запускается как файл**, а не передаётся в `bash -s` через stdin. Это принципиально: внутри есть `docker compose exec -T`, который читает stdin и в потоковом варианте съедает остаток скрипта — bash доходит до EOF и выходит с кодом 0, то есть деплой обрывается после дампа и рапортует об успехе.

Образы в GHCR:

- `ghcr.io/allas122/aiagentsberhakaton/chatnode`
- `ghcr.io/allas122/aiagentsberhakaton/web`
- `ghcr.io/allas122/aiagentsberhakaton/anonymizer`

Каждый помечается двумя тегами: `latest` и `sha-<полный sha коммита>`.

## Почему данные не теряются

Три вещи в сумме:

1. **Тома именованные** — `aiagent-sber_postgres-data`, `_seaweedfs-data`, `_valkey-data`. `docker compose up -d` их не пересоздаёт: контейнер меняется, том переживает. Убить их может только `docker compose down -v` — поэтому флага `-v` нет нигде в `remote-deploy.sh`, и добавлять его туда нельзя.
2. **Дамп до выката** — `remote-deploy.sh` первым делом снимает `pg_dump -Fc` в `~/backups/predeploy-<timestamp>.dump`. Если дамп не удался или получился пустым, скрипт падает **до** того, как что-либо тронул.
3. **Миграции аддитивные** — EF применяет их сам на старте (`ChatNode/Infrastructure/Database/DatabaseMigrator.cs:23`).

Хранятся последние 10 дампов, старые чистятся автоматически.

### Важное ограничение отката

Откат по тегу возвращает **код**, но не схему БД. Если выкаченная версия применила миграцию, откат контейнера назад оставит схему новой — старый код может не завестись на новой схеме. В этом случае нужен restore из дампа:

```bash
ssh <DEPLOY_USER>@<DEPLOY_HOST>
cd ~/app
docker compose exec -T postgres pg_restore -U grants -d grants --clean --if-exists < ~/backups/predeploy-<timestamp>.dump
```

## Как выкатить

1. Push в `main` → дождаться зелёного **Build images**.
2. Actions → **Deploy to VPS** → Run workflow → `tag` = `latest`.

## Откаты

Есть два механизма.

### Автоматический

Перед `pull` скрипт запоминает image ID работающих контейнеров и вешает на них тег `rollback-<timestamp>`. Если после выката health-check не прошёл за 240 секунд, скрипт сам поднимает контейнеры обратно с этого тега и ждёт ещё 120 секунд.

Работает на image ID, а не на digest — поэтому откат возможен даже с локально собранных образов, у которых digest нет вовсе.

Итог пишется в `~/backups/deploy-history.log`, последние три строки печатаются в начале каждого деплоя:

```
2026-08-28 14:02:11  tag=latest    result=ok           rollback_point=rollback-20260828-140044
2026-08-28 15:31:07  tag=latest    result=rolledback   rollback_point=rollback-20260828-152950
```

Выключается галочкой **rollback_on_failure** при запуске workflow — тогда сломанная версия останется на проде, чтобы её можно было живьём подебажить.

Хранятся три последние точки (`ROLLBACK_KEEP`), остальные теги снимаются в конце успешного деплоя. Это не косметика: тегированный образ не удаляется через `docker image prune`, поэтому каждая лишняя точка вечно держит на диске предыдущий образ anonymizer весом в пару гигабайт.

Даже при успешном откате workflow завершается **красным**: прод восстановлен, но выкат не состоялся, и это должно быть видно.

### Ручной

Actions → **Deploy to VPS** → Run workflow → `tag` = `sha-<полный sha коммита>`.

Работает, только если для того коммита прошла сборка. Список доступных тегов — на странице пакета в GHCR.

Точки отката (`rollback-*`) живут только на сервере, в GHCR их нет. Посмотреть, что доступно локально:

```bash
ssh <DEPLOY_USER>@<DEPLOY_HOST> "docker images 'ghcr.io/allas122/aiagentsberhakaton/*' --format '{{.Repository}}:{{.Tag}}'"
```

### Чего откат не делает

Возвращает **код, но не схему БД**. Если выкаченная версия успела применить миграцию, откат контейнера оставит схему новой — старый код может на ней не завестись. Тогда нужен restore из дампа, см. выше.

Именно поэтому дамп снимается всегда, даже когда автооткат включён.

## Секреты репозитория

Репозиторий публичный, поэтому здесь только описания. Сами значения — в Settings → Secrets and variables → Actions.

| Секрет | Что класть |
|---|---|
| `DEPLOY_HOST` | IP или домен VPS |
| `DEPLOY_USER` | SSH-пользователь на VPS |
| `DEPLOY_SSH_KEY` | приватный ключ `github-actions-deploy` целиком, вместе со строками `BEGIN`/`END` |
| `DEPLOY_KNOWN_HOSTS` | строка из `ssh-keyscan -t ed25519 <DEPLOY_HOST>` |

`DEPLOY_KNOWN_HOSTS` нужен, чтобы не отключать проверку ключа хоста: если IP начнёт отвечать чужим ключом, деплой упадёт вместо того, чтобы отдать доступ неизвестно кому. Полученный отпечаток стоит сверить с локальным `~/.ssh/known_hosts`.

`GITHUB_TOKEN` создаётся автоматически — заводить не нужно. Им же workflow логинится в GHCR на самом сервере, поэтому делать пакеты публичными не обязательно.

## Переменные репозитория

Settings → Secrets and variables → Actions → вкладка **Variables**. Не секреты — значения не скрываются, это нормально.

| Variable | Если не задана | Зачем |
|---|---|---|
| `PII_MODEL_SOURCE` | `Wismut/nym-pii-multilingual` | Откуда брать PII-модель при сборке anonymizer |
| `PII_MODEL_REVISION` | пусто = последняя | Пин на конкретный коммит модели в Hugging Face |

Модель запекается в образ на этапе сборки (`AnonimyzeService/Dockerfile:37-45`), в рантайме сеть ей не нужна.

`PII_MODEL_REVISION` стоит задать перед сдачей: без пина сборка тянет текущий `main` модели, и если её обновят на Hugging Face, соседние сборки одного и того же коммита дадут разные образы. Взять sha ревизии — на странице модели, вкладка Files and versions.

## Что живёт только на сервере

`~/app/.env` — в git его нет и быть не должно (репозиторий публичный). Деплой копирует на сервер `docker-compose.yml`, `docker-compose.prod.yml` и `remote-deploy.sh`, `.env` не трогает. Новую переменную нужно добавить руками на сервере **до** выката, иначе применится дефолт из `docker-compose.yml`.

## Ручной запуск с сервера

```bash
ssh <DEPLOY_USER>@<DEPLOY_HOST>
cd ~/app
IMAGE_TAG=latest bash ~/app/remote-deploy.sh
```
