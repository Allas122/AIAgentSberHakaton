# ИИ-помощник проректора

RAG-ассистент аппарата проректора: база знаний, грантовые заявки, деловая переписка, поручения.
Собран под хакатон Сбера, работает на GigaChat.

Проректор загружает документы в **базу знаний** — положение о конкурсе, регламент, выгрузку
мониторинга. Текст разбирается на части и индексируется в PostgreSQL как векторное хранилище
(pgvector), таблицы кладутся рядом отдельными датасетами. Дальше с этой базой можно работать
пятью способами:

- **Спросить.** Консультант отвечает строго по загруженному документу, а не по своим знаниям.
- **Посчитать по таблице.** «Сколько у нас очников-сирот», «какая общая сумма по факультетам» —
  считает код по строкам `.csv`/`.xlsx`, модель только пересказывает результат.
- **Проверить заявку.** Загружаете `.docx` — получаете разбор: балл по каждому критерию, что
  нарушено, что требует уточнения, каких разделов не хватает. Отдельным блоком — расхождения в смете,
  посчитанные кодом, а не моделью.
- **Ответить на письмо.** По одному из трёх встроенных видов или своему шаблону, с подставленными
  реквизитами организации и автоматическим извлечением поручений из текста.
- **Вести поручения.** Список задач с исполнителями, сроками и статусами.

Тяжёлая работа идёт в фоне. Файл встаёт в очередь, воркер забирает его и присылает результат через
SignalR — закрытая вкладка проверку не отменяет.

> В коде и в API база знаний называется `manual` (`/api/manuals`, `ManualParserAgent`,
> таблицы `manuals` / `manual_parts`). Исторически туда грузили только методичку; смысл расширился,
> имена остались.

## Запуск за пять минут

Нужен Docker Desktop или Docker Engine с Compose v2.

**1. Заведите `.env`:**

```powershell
copy .env.example .env
```

**2. Заполните пять обязательных ключей** — каждый из них объявлен в `docker-compose.yml` через
`:?`, так что без них `docker compose` откажется стартовать:

```dotenv
GIGACHAT_AUTHORIZATION_KEY=<ключ авторизации GigaChat в base64>
JWT_SECRET_KEY=<случайная строка от 32 символов>
POSTGRES_PASSWORD=<пароль к базе>
STAFF_RECTOR_PASSWORD=<пароль проректора>
STAFF_COORDINATOR_PASSWORD=<пароль координатора>
```

В `.env.example` на месте паролей стоит `CHANGE_ME` — это рабочее значение, но именно им вы и будете
входить. Логины по умолчанию — `prorektor` и `koordinator`.

Секрет JWT удобно сгенерировать так:

```powershell
[Convert]::ToBase64String((1..48 | % { Get-Random -Max 256 }))
```

**3. Поднимите:**

```powershell
docker compose up -d --build
docker compose logs -f chatnode
```

Первая сборка долгая — образ анонимайзера тянет с Hugging Face NER-модель на 1–2 ГБ и запекает её
внутрь. Это происходит один раз; дальше старт быстрый и сети не требует.

**4. Проверьте, что поднялось:**

| Что | Адрес |
|---|---|
| **Интерфейс** — сюда и заходить | http://localhost:8080 (вход `prorektor` / пароль из `.env`) |
| Scalar UI | http://localhost:5064/scalar (только при `ASPNETCORE_ENVIRONMENT=Development`) |
| OpenAPI | http://localhost:5064/openapi/v1.json (там же) |
| SeaweedFS filer | http://localhost:8888 |

`docker compose ps` должен показать все сервисы в `healthy`/`running`, а `seaweedfs-init` —
в `exited (0)`: это одноразовый контейнер, который создаёт бакет и завершается.

**5. Пройдите сценарий целиком:**

1. Войдите проректором, загрузите в базу знаний положение о конкурсе (`.md`, `.docx` или `.pdf`)
   в панели слева и дождитесь стадии `Ready`.
2. Задайте по нему вопрос в чате — консультант ответит цитатами из документа.
3. Загрузите туда же выгрузку мониторинга `.xlsx` и спросите «сколько строк по каждому факультету» —
   число посчитает код.
4. Приложите к сообщению `.docx`-заявку и выберите тип конкурса. Разбор придёт в чат сам.
5. Заполните карточку организации в разделе «Организация», затем ответьте на письмо в «Письмах».
6. Загляните в «Поручения», «Загруженные файлы» и «Токены».

Остановка и полная очистка данных:

```powershell
docker compose down       # остановить
docker compose down -v    # остановить и стереть тома
```

## Что внутри интерфейса

Семь разделов, доступ зависит от роли.

| Раздел | Путь | Кому | Что делает |
|---|---|---|---|
| Заявки | `/chat` | всем, включая гостей | Диалог с консультантом, загрузка `.docx` или `.pdf` на проверку, скачивание заявки и разбора прямо из вложения в чате |
| Деловая переписка | `/letters` | `Rector` | Ответ на письмо (`.docx` или `.pdf`) по одному из трёх видов, извлечение поручений из текста |
| Поручения | `/assignments` | `Rector`, `Coordinator` | Список задач: исполнитель, срок, статус |
| Загруженные файлы | `/files` | `Rector`, `Coordinator` | Реестр загруженного, статус разбора, скачивание |
| Расход токенов | `/usage` | `Rector`, `Coordinator` | Сколько потрачено по операциям и моделям; чистить журнал может только `Rector` |
| Учётные записи | `/accounts` | `Rector` | Создание и удаление учёток, смена роли и пароля |
| Организация | `/organization` | `Rector` | Карточка организации, реквизиты, подпись и контактное лицо для писем |

Кроме обычного чата по заявке, staff может завести **служебный чат** (кнопка в панели слева).
Это тот же консультант, но работает он со служебной частью базы знаний и ведёт поручения.

### Две базы знаний

База знаний разделена на два списка, и граница проходит **по типу чата**, а не по роли:

| Список | `Scope` | Где доступен | Что туда кладут |
|---|---|---|---|
| Служебный | `Staff` | Только в служебных чатах | Мониторинги, выгрузки, отчёты, внутренние регламенты |
| Общий | `Public` | Везде, включая гостей и студентов | Положения о конкурсах, инструкции для заявителей |

Служебный чат заводит только staff, поэтому отдельная проверка роли не нужна: до служебного
списка попросту неоткуда дотянуться. В служебном чате видны **оба** списка (в выпадающем списке
они разделены на «Служебные» и «Общие») — координатору нужны и внутренний мониторинг, и положение
о конкурсе. В обычном чате виден только общий список.

Разделение держится не на том, что фронт чего-то не показывает. `ChatService.EnsureManualAllowedAsync`
проверяет выбранный документ на каждом обращении — и в диалоге, и при загрузке заявки, — а
`GET /api/manuals` фильтрует список по роли. Подставить чужой `manualId` в запрос нельзя.

**Ответ на попытку — `404`, а не `403`.** Иначе по коду ответа можно было бы перебором выяснить,
какие служебные документы существуют: `403` означал бы «документ есть, но не для вас».

Отчёты закрываются тем же признаком. Таблица привязана к документу, из которого она разобрана,
поэтому `list_datasets` и `query_dataset` в обычном чате видят только таблицы из общих документов.
Инструменты у агента остаются, но выборка приходит уже отфильтрованной — посчитать по служебному
мониторингу из студенческого чата нельзя, даже зная его название.

Выбранный документ запоминается **отдельно** для каждого списка (`chatnode.manual`
и `chatnode.manual.staff`): переключение между обычным и служебным чатом не сбрасывает выбор
и не тащит служебный документ туда, где он недоступен.

При загрузке список выбирается переключателем, по умолчанию — **служебный**. Ошибка в эту сторону
безобидна и сразу заметна: документ не появится у студентов. Обратный дефолт означал бы, что забытый
переключатель выкладывает мониторинг с персданными наружу.

Документы, загруженные до появления разделения, миграция пометила общими — они и были доступны всем,
и терять этот доступ на ровном месте незачем.

### Роли

| Роль | Как появляется | Права |
|---|---|---|
| `Guest` | Автоматически при первом заходе, живёт в Valkey с TTL | Чат и проверка заявок |
| `User` | Самостоятельная регистрация или заводит проректор | **Ровно те же, что у гостя** |
| `Coordinator` | Заводит проректор или seeder из `.env` | Плюс поручения, реестр файлов, расход токенов, служебные чаты и загрузка в базу знаний |
| `Rector` | Seeder из `.env`, дальше — из базы | Всё, включая учётки, письма, шаблоны и карточку организации |

Граница прав в системе ровно одна: `Rector` и `Coordinator` — служебные роли (staff). Всё, что не
относится к работе с собственной заявкой — реестр файлов, поручения, загрузка документов, учётки,
письма, расход токенов, — доступно только им.

`Guest` и `User` по возможностям неразличимы. Регистрация ничего не открывает; она нужна, чтобы чаты
и разобранные заявки не пропали вместе с гостевой сессией и были доступны с другого устройства.

Себя разжаловать или удалить нельзя, последнего проректора удалить тоже нельзя — иначе управлять
учётками стало бы некому.

## Архитектура

Три сервиса и четыре хранилища, всё поднимается одним `docker compose`.

```
                  браузер
                     │
                  [ web ]  nginx: статика + прокси /api и /chat-hub
                     │
                [ chatnode ]  .NET 10: REST, SignalR, агенты, воркеры
                 ╱   │   │  ╲
        postgres  valkey  s3  [ anonymizer ]  Python: gRPC, вырезание ПДн
        +pgvector                  │
                                GigaChat
```

### `ChatNode` — .NET 10, ASP.NET Core

REST API, SignalR-хаб, агенты, фоновые воркеры, работа с PostgreSQL, Valkey и S3. Слушает `8080`
в контейнере, наружу проброшен на `5064`.

Внутри одного проекта три слоя папками, у каждого свой DI-extension, вызываемый в `Program.cs`:
`Infrastructure` → `Application` → `Api`. `Domain` — отдельная библиотека с сущностями и интерфейсами
репозиториев, без зависимостей. Направление зависимостей Api → Application → Infrastructure → Domain,
но `Application` напрямую использует типы `Infrastructure`, так что это не строгий onion.

Четыре агента поверх GigaChat, все с function calling:

| Агент | Что делает | Модель по умолчанию |
|---|---|---|
| `ManualParserAgent` | Режет документ на части и наполняет RAG-индекс | `GigaChat-2-Max` |
| `ConsultingAgent` | Отвечает по базе знаний, считает по таблицам, читает находки проверки | `GigaChat-2-Pro` |
| `ApplicationReviewAgent` | Проверяет `.docx`-заявку по документу и собирает разбор | `GigaChat-2-Max` |
| `LetterAgent` | Готовит ответ на письмо и вытаскивает из него поручения | `GigaChat-2-Pro` |

Полный набор инструментов агентов:

| Группа | Инструменты |
|---|---|
| База знаний | `get_manual_full_navigation`, `search_in_manual`, `add_manual_part`, `add_manual_navigation_header` |
| Таблицы | `list_datasets`, `query_dataset` |
| Находки проверки | `create_pin`, `update_pin`, `delete_pin`, `get_pins`, `search_pins`, `get_application_review` |
| Поручения | `create_assignment`, `update_assignment_status`, `list_assignments` |
| Календарь | `get_current_datetime`, `resolve_date`, `date_difference` |
| Прогресс | `send_status_of_processing` |

Календарные инструменты нужны, чтобы «до конца недели» превращалось в дату. Часовой пояс агента —
`Europe/Moscow` (`GigaChat__AgentTimeZoneId`), но клиент передаёт свой в
`SendMessageToConsultingAgent(..., timeZone)`, и он побеждает.

Эндпоинты GigaChat требуют российских корневых сертификатов: `Resources/*.cer` встроены в сборку
и подключаются ко всем HTTP-хендлерам GigaChat.

### `AnonimyzeService` — Python 3.11, gRPC

Убирает персональные данные из текста до того, как он уйдёт в GigaChat. Слушает `50051`.
Мультиязычная NER-модель `Wismut/nym-pii-multilingual` плюс regex с проверкой контрольных сумм для
ИНН и СНИЛС. Найденное заменяется тегами `[TYPE_XXXX]`, соответствие «тег → оригинал» кладётся
в Valkey под ключ `anon:{sessionId}` на 24 часа, чтобы ответ агента можно было деанонимизировать.

Куски текста уходят в пайплайн **пачкой** (`NER_BATCH_SIZE`, по умолчанию 8), а не по одному: на
разборе заявки их сотни, и по одному это упиралось в накладные расходы вызова. Если пачка упала
целиком, она переразбирается по одному куску — один битый фрагмент не должен ронять остальные.

Модель **вшивается в образ на `docker build`** через `save_pretrained` в `/opt/models/pii-model`,
рантайму сеть и тома не нужны. Раньше она тянулась с Hugging Face при первом старте — без доступа
к HF контейнер не становился healthy, а `chatnode` ждёт его через `depends_on: service_healthy`,
то есть не поднималось вообще ничего.

Контракт лежит **в двух копиях**: `ChatNode/Protos/anonymize_service.proto` и
`AnonimyzeService/protos/anonymize_service.proto` — править нужно оба. C#-клиент генерируется
на сборке через `Grpc.Tools`, Python-стабы в `AnonimyzeService/generated/` закоммичены и после
правки proto перегенерируются руками (`grpcio-tools` нужен только для этого и в `requirements.txt`
намеренно не входит):

```powershell
pip install grpcio-tools
python -m grpc_tools.protoc -I AnonimyzeService/protos --python_out=AnonimyzeService/generated --grpc_python_out=AnonimyzeService/generated AnonimyzeService/protos/anonymize_service.proto
```

### `frontend` — React 19, Vite, TypeScript

SPA на React Router, SignalR-клиент, без UI-библиотек. Собирается в образ `web` и раздаётся
nginx-ом, он же проксирует `/api` и `/chat-hub` на `chatnode`. Всё живёт на одном origin, поэтому
CORS не нужен и в бэкенде не настроен.

### Инфраструктура

| Сервис | Зачем | Порт |
|---|---|---|
| `postgres` | Образ `pgvector/pgvector:pg17`. Постоянные данные и **векторный поиск** по базе знаний | `5432` |
| `valkey` | Кеш, чаты и сообщения, находки проверки, очереди разбора, карты обезличивания | `6379` |
| `seaweedfs` | S3-совместимое хранилище файлов | `8333` (S3), `8888` (filer), `9333` (master) |
| `seaweedfs-init` | Одноразовый контейнер: создаёт бакет и завершается | — |
| `anonymizer` | gRPC-сервис обезличивания | `50051` |
| `chatnode` | Бэкенд | `5064` → `8080` |
| `web` | nginx: фронт и прокси | `8080` → `80` |

### Что где лежит

Разделение не интуитивное, поэтому явно.

**PostgreSQL — источник истины и векторное хранилище.** Схема накатывается EF-миграциями
автоматически при старте `chatnode`, руками ничего запускать не нужно; расширение `vector`
создаётся той же миграцией.

| Таблица | Что |
|---|---|
| `user_accounts` | Учётки с PBKDF2-хешами паролей |
| `manuals`, `manual_parts` | Документы базы знаний (`Scope`: `Staff` или `Public`), их разобранные части и эмбеддинги |
| `datasets`, `dataset_columns`, `dataset_rows` | Таблицы из `.csv`/`.xlsx`: колонки с определённым типом, строки в `jsonb` |
| `organization_profiles` | Карточка организации: реквизиты, подписант, контактное лицо |
| `stored_documents` | Реестр загруженного: кто, в какой чат, какой файл, ключ в S3 |
| `assignments` | Поручения |
| `letter_templates` | Свои шаблоны ответов на письма (встроенные виды — в коде); у шаблона-бланка здесь ключ `.docx` в S3 и список найденных меток |
| `application_reviews`, `application_review_criteria` | Сохранённые разборы заявок с баллами по критериям |
| `token_usage` | Журнал расхода токенов по операциям и моделям |

Эмбеддинг части лежит в двух колонках: историческая `Embedding` (`bytea`) и рабочая
`EmbeddingVector` (`vector(1024)`) с HNSW-индексом по косинусу. Поиск идёт по второй.

**Valkey — оперативное состояние с TTL.** Данные здесь **протухают через сутки** (настраивается
блоком `EXPIRATION_*`).

| Ключ | Что |
|---|---|
| `pin:{sessionId}:{pinId}`, `pins:{sessionId}` | Находки агента по текущей проверке заявки: хеш на находку и сортированный набор-указатель |
| `anon:{sessionId}` | Карта «тег → оригинал» для деанонимизации, TTL 24 ч |
| `review:jobs` | Stream очереди разбора заявок, consumer group `reviewers` |
| `manual:jobs` | Stream очереди разбора документов, consumer group `manual-parsers` |
| `review:status:{ownerId}` | Стадия разбора по каждому документу |
| чаты, сообщения, гости, ws-тикеты | Сообщения — Redis Stream, текст лежит как есть; у сообщения с вложением есть `DocumentId` и `FileName`. Гостевые аккаунты в базу не пишутся |

Векторных индексов в Valkey больше нет. `ValkeyIndexInitializer` теперь только сносит оставшиеся
с прошлых версий `idx:manual_parts_v2` и `idx:pins` и молча проходит мимо, если модуля поиска
в образе нет вовсе.

**S3 (SeaweedFS) — файлы.** Документы базы знаний, загруженные заявки, бланки писем
(`letter-forms/`) и готовые исходящие письма (`letters/`).

> **Важно.** В хранилище заявка кладётся **как есть, с исходными персданными**. Обезличивание живёт
> только на границе с моделью: копия для GigaChat чистится на лету и никуда не сохраняется.
> Следствие — в бакете лежат настоящие персональные данные, и доступ к нему нужно ограничивать
> соответственно. В compose порты SeaweedFS привязаны к `127.0.0.1`.

## Как это работает

### Загрузка в базу знаний

Принимаются шесть форматов, и от формата зависит, что получится:

| Формат | Что делает `KnowledgeDocumentReader` |
|---|---|
| `.md`, `.txt` | Берёт текст как есть |
| `.docx` | Собирает markdown: заголовки по стилям, таблицы — markdown-таблицами |
| `.pdf` | Вытаскивает текстовый слой постранично (`PdfPig`). Скан без текстового слоя вернёт пусто и будет отклонён |
| `.csv`, `.xlsx` | Разбирает **в таблицы**: они и уходят в датасеты, и рендерятся в markdown для текстового индекса |

Запрос не ждёт разбора. `POST /api/manuals/upload` кладёт файл в S3, заводит запись в реестре
документов и ставит задачу в поток Valkey `manual:jobs`, после чего сразу отвечает `202` с
`manualId` и стадией `Queued`. Дальше работает `ManualParseWorker`: забирает задачу, качает файл
из S3 и запускает разбор. Зависшие задачи подбираются по `XPENDING` через 30 минут, максимум
две попытки.

Перед разбором текст обрезается до `MANUAL_MAX_TEXT_CHARS` (400 000 символов, по границе строки)
с записью в лог. Это не про качество, а про деньги и время: 400 тысяч символов — это и так сотня
запросов к модели.

`ManualParserAgent` режет текст на куски примерно по 4000 символов по структурным границам,
с перекрытием в 500 символов, и скармливает модели по одному — перекрытие идёт как «уже
обработанный» контекст. На этом проходе агенту выдаются **только три инструмента**
(`add_manual_part`, `add_manual_navigation_header`, `get_manual_full_navigation`): поиск и прочее
ему здесь не нужны, а каждая лишняя схема инструмента уезжает в промпт на каждом витке цикла.
Куски, которые упали или исчерпали бюджет вызовов, собираются в список и проходят второй раз
половинным размером: один сбойный кусок больше не роняет весь документ.

Стадия разбора живёт в таблице `manuals` (`Stage`, `TotalChunks`, `ProcessedChunks`, `FailedChunks`,
`StatusDetail`) и параллельно уходит владельцу по SignalR событием `ManualStatus`:
`Queued` → `Parsing` (с прогрессом) → `Ready`, `Partial` или `Failed`.

`Partial` означает, что часть фрагментов в базу знаний не попала. В `StatusDetail` и в поле `gaps`
события перечислены их заголовки и причина — чтобы было видно, что именно осталось непроверяемым.
Если не разобрался ни один фрагмент, стадия `Failed`. Фронт держит документы в неготовых стадиях
под опросом раз в 7 секунд, показывает статус в панели слева и не даёт отправлять по ним заявки.

Части и их эмбеддинги сохраняются в PostgreSQL, поиск идёт по HNSW-индексу pgvector прямо в базе.
Прогрева кеша больше нет: раньше части лежали ещё и в Valkey под `manualpart:*`, и перед каждым
поиском репозиторий проверял, «тёплый» ли индекс. Держать вторую копию с TTL ради поиска по данным,
которые и так лежат в PostgreSQL, оказалось дороже, чем искать в самой PostgreSQL.

### Таблицы и подсчёт

Каждая таблица из `.csv`/`.xlsx` становится датасетом: имя листа, колонки с определённым типом
(`Number`, `Date`, `Text` — по доле распознанных значений в 80 %) и строки в `jsonb`. Строки
пишутся через явную конвертацию `Dictionary` → JSON в `DatasetRowConfiguration`: Npgsql
с версии 8 отказывается писать словарь в `jsonb` без включённой динамической сериализации,
и без этой конвертации загрузка таблицы падала на `SaveChangesAsync`. Шапкой
считается первая строка, где заполнено хотя бы две ячейки; дубли имён колонок разводятся суффиксом
`(2)`. Потолок — 50 000 строк и 64 колонки на таблицу.

Датасеты привязаны к документу: повторная загрузка того же файла сначала удаляет прежние
(`DeleteByManualAsync`), а удаление документа сносит их каскадом. Осиротевших таблиц не остаётся.
Оттуда же берётся и видимость: таблица доступна ровно там, где доступен её документ, — служебная
не видна в студенческом чате, см. «Две базы знаний».

У консультанта и у агента писем есть два инструмента:

- `list_datasets` — какие таблицы есть, сколько строк, какие колонки и примеры значений в них.
  Промпт требует звать его первым: без точных названий колонок запрос не построить.
- `query_dataset` — `count`, `sum`, `average`, `min`, `max`, с фильтрами и группировкой.
  Фильтры — строкой через точку с запятой: `Форма обучения=Очная; Категория~сирот; Курс>=3`.
  Операторы: `=`, `!=`, `~` (содержит), `>`, `<`, `>=`, `<=`.

**Считает `DatasetQueryEngine`, а не модель.** Она получает готовое число и строку `explain`
(«Посчитано кодом по таблице «…» (37 из 412 строк): сумма по колонке «Объём» — 1 240 000»), и промпт
прямо запрещает пересчитывать и округлять. Названия колонок движок сопоставляет нестрого: точное
совпадение, затем вхождение подстроки, и только потом сдаётся. Всё, что при этом пропущено —
не найденная колонка, нечисловые значения в числовой колонке, — уходит в `notes`, а промпт требует
пересказать их пользователю. Молча посчитать по половине строк нельзя.

### Диалог

`ConsultingAgent` отвечает по результатам KNN-поиска `search_in_manual` и обязан звать
`send_status_of_processing` перед каждым долгим действием, чтобы пользователь видел прогресс.
Дополнительно он получает read-only доступ к находкам проверки заявки в том же чате (`get_pins`,
`search_pins`) — так что после проверки можно спросить «а что было не так».

Оглавление документа урезается до 4000 символов: у большой методички оно само по себе занимало
столько же, сколько содержательный ответ поиска. В обрезанный хвост дописывается подсказка искать
недостающие разделы через `search_in_manual`.

В историю сохраняются только текстовые ответы, результаты вызовов инструментов — нет. Системный
промпт поэтому явно требует искать заново, а не пересказывать собственный прошлый ответ.

Лимиты страниц зажаты в коде: список чатов и историю сообщений можно запросить не больше чем
по 100 записей, значение по умолчанию — 10. Клиент, попросивший миллион, получит сотню.

### Проверка заявки: очередь

`POST /api/chat/{chatId}/files` **не проверяет заявку синхронно.** Он кладёт файл в S3, регистрирует
его в `stored_documents`, ставит задание в Valkey Stream `review:jobs` и отвечает `202` с глубиной
очереди. Разбор идёт в фоне, закрытая вкладка его не отменяет.

Сообщение о загрузке — не текст. В поток чата пишется только комментарий пользователя (часто
пустой), а сам файл живёт в полях `DocumentId` и `FileName` того же сообщения. Фронт рисует по ним
виджет вложения с кнопками «Заявка» и «Разбор»; вторая появляется, когда для этого `documentId`
находится сохранённый разбор.

`ReviewWorker` — `BackgroundService`, читающий стрим через consumer group `reviewers`. Задание
подтверждается (`XACK` + `XDEL`) только после успеха. Если воркер умер посреди работы, задание
зависает в pending-списке; через 10 минут простоя его подбирает `ReclaimAsync`, а после трёх попыток
оно снимается с очереди и пользователю в чат уходит сообщение о неудаче.

Ошибки делятся на постоянные и временные. `InvalidDocumentException`, `NotFoundException` и
`FileNotFoundException` — постоянные: повторять их бессмысленно, задание сразу снимается с очереди,
а пользователь получает причину. Остальное возвращается в очередь.

Перед разбором `RunApplicationReviewAsync` проверяет, что чат ещё существует. Проверка стоит
до первого обращения к модели намеренно: без неё разбор заявки из удалённого чата отрабатывал
целиком — минуты работы и полный расход лимитов GigaChat — и падал в самом конце, когда результат
уже некуда сохранять.

Исключения-«не найдено» живут в одном месте, `ChatNode.Application.Exceptions`. Раньше рядом
существовала вторая иерархия `ChatNode.Infrastructure.Exceptions` с одноимённым `NotFoundException`:
репозиторий бросал инфраструктурный, а воркер и обработчик HTTP-ошибок сопоставляли прикладной.
Типы разные, совпадение по `is` не срабатывало — задание считалось временной ошибкой и висело три
попытки, а REST отдавал `500` вместо `404`.

Прогресс пишется в `review:status:{ownerId}` и параллельно уходит в SignalR-группу пользователя,
поэтому раздел «Файлы» показывает стадию разбора даже после перезагрузки страницы.

### Проверка заявки: разбор

Файл забирается из S3 → ПДн вычищаются (ключ сессии = `chatId`) → анонимизированный текст режется
на секции → `ApplicationReviewAgent` идёт по ним **строго по одной** → результат деанонимизируется
и добавляется в чат сообщением агента.

Чистка зависит от формата, и это не косметическая разница:

| Формат | Как убираются ПДн | Как получаются секции |
|---|---|---|
| `.docx` | `DocxAnonymizer` правит **сам файл**: агент получает очищенную копию документа | По стилям заголовков, outline level и жирному тексту |
| `.pdf` | Текст извлекается `PdfPig`, затем строки чистятся пачкой (`AnonymizeBatchAsync`) | `PlainTextSections` по текстовой эвристике: нумерация «1.2», слова «Раздел», «Приложение», строка капсом |

Для PDF правки «внутри файла» не существует — там нет структуры документа, которую можно
переписать, — поэтому чистится извлечённый текст. Порядок при этом сохраняется прежний:
сначала обезличивание, только потом нарезка на секции.

Заголовки в PDF угадываются по виду строки, так что деление на секции получается грубее, чем
в docx. На результат это влияет мягко: агент всё равно переупаковывает секции под бюджет
(`PackSections`), а если заголовков не нашлось вовсе, документ идёт одной секцией и режется
по размеру. Скан без текстового слоя отклоняется сразу — OCR в системе нет.

Порядок «сначала анонимизация, потом нарезка» не случаен, и параллелить фрагменты нельзя: контекст
фрагмента об остальном документе — это хранилище находок и накопительная сводка, и при конкурентной
обработке двенадцатый фрагмент прочитает и то и другое наполовину заполненными.

Фрагменты связаны накопительной сводкой: после каждого в неё сливается всё, что агент записал,
изменил или удалил, а следующий получает её хвост в промпте. Сводку ведёт код, инструментов для её
правки у модели нет — поэтому удалить находку она может, а «забыть» прочитанный раздел нет.

Отдельный проход `ExtractCriteriaAsync` вытаскивает из документа критерии оценки под выбранный тип
конкурса; их названия уходят в промпт каждой секции. Если критериев в документе нет, извлечение
возвращает пусто и разбор деградирует до простого списка находок — критерии не выдумываются.

**Проход по секции не имеет права заявлять, что чего-то нет.** Он видит один фрагмент из многих,
и «бюджет не указан» почти всегда ложь: бюджет в соседнем фрагменте. Реальные пропуски ищет
`CheckCoverageAsync` — единственное место с обзором всего документа. Формулировки отсутствия
в находках принудительно понижаются до «проверить вручную».

Теги вида `[PER_0001]` в тексте — **не дефект заявки**: значение есть, оно просто скрыто
от проверяющего. Это зафиксировано и в промптах, и в коде.

### Баллы считает код, а не модель

Это ключевое решение всего разбора. Модель находит проблемы, но **не выставляет оценки**.

`ReviewConsolidator` сопоставляет находки с критериями и считает балл детерминированно:

| Вывод | Балл |
|---|---|
| Замечаний нет | максимум по критерию |
| Требует уточнения | `round(max × 0.7)`, но не ниже половины максимума |
| Нарушение | `round(max × 0.3)` |
| Раздел не найден | `0` |

Каждая находка сверх первой снимает ещё балл в пределах тех же границ. Дубли отсеиваются по первым
80 символам нормализованного текста.

После этого `ReviewNarration` отправляет модели уже посчитанный результат с единственной задачей —
объяснить его человеческим языком, по строке на критерий. Системный промпт прямо запрещает спорить
с выводом и менять балл. Собранный `ApplicationReviewResult` сохраняется в `application_reviews` /
`application_review_criteria`, а `ReviewRenderer` печатает его в markdown.

### Смету тоже считает код

`ApplicationNumbersAnalyzer` разбирает числовые разделы заявки без участия модели и проверяет:

- сумму строк сметы против заявленной общей суммы;
- **произведение цены на количество в каждой строке** против указанной суммы;
- плановые показатели против того, что просуммировано по разделам мероприятий и публикаций;
- обещания вида «не менее N» в формулировке цели против плановых значений;
- доли категорий расходов, запрошенную сумму на одного участника, долю софинансирования.

Найденные расхождения уходят в разбор отдельным блоком «Проверено расчётом» с явной пометкой, что
они посчитаны по документу, а не выведены моделью, и попадают в промпт `ReviewNarration` как
проверенные факты с требованием переносить числа дословно.

Строка сметы, где произведение не сходится с суммой, печатается как
`1 000 руб. × 5 = 5 000 руб. ≠ 50 000 руб.` — знак `≠` показывает, что равенство не выполняется.
Случай, когда общая сумма сходится, а отдельная строка внутри себя противоречива, ловится именно
здесь: проверки итога для него недостаточно.

### Письма

`LetterAgent` получает текст письма (из `.docx`, `.pdf` или вставленный руками), намерение ответа,
вид письма и два блока собственных данных — карточку организации и адресата. Работает на своей
модели (`GIGACHAT_LETTER_MODEL`), отдельной от консультанта: письмо и диалог — разные задачи,
и переключать одно, не трогая другое, оказалось нужно чаще, чем казалось.

Шаблон уходит в модель как обязательная структура: она повторяет его блоки и формулировки,
подставляя данные из письма, а незаполненные плейсхолдеры перечисляет в конце под заголовком
«Требуется уточнить». Параллельно агент вытаскивает из письма поручения — они создаются в разделе
«Поручения» с источником `Letter`.

Цифры в письмо агент берёт не из головы: у него есть `list_datasets` и `query_dataset`, и промпт
требует поднимать любой показатель — численность, сумму, долю — через них. Если подходящей таблицы
нет, на месте числа остаётся плейсхолдер.

#### Три вида письма

Встроены в код (`LetterPresets`), а не в базу: их нельзя удалить, они одинаковы у всех и
появляются сразу, без сидера и миграции. Свои шаблоны заводятся рядом и правятся как раньше.

| Вид | Что делает |
|---|---|
| Ответ: ответственный и контакты | Называет ответственного и даёт его контакты |
| Сопроводительное к мониторингу | Сообщает, что данные заполнены, и ссылается на приложение |
| Ответ на жалобу | Разбор доводов обращения и порядок обжалования |

Плейсхолдеры шаблонов — в угловых скобках (`<ПОДПИСЬ>`, `<КОНТАКТНОЕ ЛИЦО>`), потому что
квадратные заняты тегами обезличивания вида `[SURNAME_0001]`, и путать их между собой нельзя.

#### Ответ файлом на бланке

Шаблон можно загрузить не только текстом, но и **бланком** — своим реальным исходящим письмом
в `.docx`, где переменные куски заменены метками в угловых скобках. Тогда ответ приходит готовым
файлом в том же оформлении: с гербом, реквизитами, подписью и строкой исполнителя.

Разметку сотрудник расставляет **руками в Word** — автоматической она не делается намеренно:
бланк у каждого ведомства свой, а ошибка разметки в официальном письме дороже, чем минута работы.

| Метка | Откуда берётся |
|---|---|
| `<ТЕЛО>` | Текст, написанный моделью |
| `<АДРЕСАТ>`, `<ОБРАЩЕНИЕ>` | Поля формы ответа; обращение по роду выбирает `RussianNameGender` |
| `<ПОДПИСЬ_ДОЛЖНОСТЬ>`, `<ПОДПИСЬ_ФИО>`, `<ПОДПИСЬ>` | Карточка организации |
| `<КОНТАКТНОЕ ЛИЦО>` | Карточка организации, собирается в одну фразу |
| `<ИСПОЛНИТЕЛЬ_ФИО>`, `<ИСПОЛНИТЕЛЬ_ТЕЛЕФОН>` | Карточка организации, обычно стоят в колонтитуле |
| `<ИСХ_НОМЕР>`, `<ИСХ_ДАТА>`, `<НА_НОМЕР>`, `<НА_ДАТА>` | Поля «Регистрация» формы ответа |
| `<ПОЛНОЕ НАИМЕНОВАНИЕ ОРГАНИЗАЦИИ>`, `<АДРЕС>`, `<ТЕЛЕФОН>`, `<ОКПО>`, `<ИНН>` и прочие реквизиты | Карточка организации |

Подстановкой занимается `DocxTemplateFiller`. Три вещи, которые он обязан делать, иначе бланк
рассыпается:

- **склеивать текст абзаца перед поиском метки.** Word рвёт строку на произвольные фрагменты, и
  `<ТЕЛО>` в файле реально может лежать как `<ТЕ` + `ЛО` + `>`. Поиск по отдельным фрагментам такую
  метку не найдёт;
- **идти по совпадениям справа налево** — иначе на строке `На № <НА_НОМЕР> от <НА_ДАТА>` подстановка
  первой метки сдвинет позицию второй;
- **обходить колонтитулы, а не только тело документа**: строка «Исп. …» живёт в `footer1.xml`.

Многострочное значение разворачивается в **настоящие абзацы**, если метка стоит в абзаце одна.
Так тело письма получает выключку по ширине и красную строку — это свойства абзаца, переносом
строки внутри одного абзаца их не добиться.

Пустые значения не оставляют `<ПОДПИСЬ>` напечатанным в документе: известные метки вычищаются,
регистрационные заменяются прочерками `__________` (как в исходном бланке), а список незаполненного
уходит в предупреждения. Письмо с меткой в угловых скобках могут подписать и отправить, не заметив.
Незнакомые метки, наоборот, остаются как есть: удалять текст из официального письма по догадке
нельзя, а по списку в предупреждениях видно опечатку.

**Модель в этом режиме пишет только тело.** Обычный промпт велит ей начинать с адресата и обращения
и заканчивать подписью — на бланке всё это уже напечатано, и получилось бы письмо с двумя
обращениями и двумя подписями. Поэтому при выбранном бланке включается `LetterOutputMode.BodyOnly`:
отдельный промпт, который запрещает адресата, обращение, подпись, контакты, приложение и номера,
а бланк показывает только как окружение слота `<ТЕЛО>`. Если модель всё же начала с «Уважаемый…»,
код отрезает эту строку и предупреждает.

Готовое письмо кладётся в S3 и в реестр как `GeneratedDocument` — оно видно в «Загруженных файлах»
с маркером персданных (там ФИО адресата) и скачивается обычным `GET /api/documents/{id}/content`.
Файл формируется в момент подготовки ответа, а не при скачивании: повторный вызов модели завёл бы
дубли поручений.

Рядом есть кнопка «Проверить бланк» (`GET /api/letter-templates/{id}/preview.docx`) — заливает бланк
данными карточки и демо-текстом **без обращения к модели**. Проверять разметку ей быстрее и дешевле,
чем полным прогоном.

#### Откуда берутся контакты и подпись

Из карточки организации (`/organization`), и **только** оттуда. Это не косметика: пока карточки
не было, модель видела вместо контактов теги обезличивания, и в блок «Контактное лицо» уезжала
единственная доступная ей почта — почта отправителя из входящего письма. Теперь в системном
промпте стоит запрет брать контакты, реквизиты и подпись откуда-либо, кроме этого блока, а пустые
поля остаются плейсхолдерами и попадают в «Требуется уточнить». Отдельным правилом оговорено, что
ИНН, ОГРН, ОКПО и КПП — реквизиты, а не контакты, и в блок «Контактное лицо» не идут никогда.

#### Обращение и пол адресата

Род обращения выбирает **код**, а не модель: `RussianNameGender` разбирает отчество
(`-ович` / `-овна` — практически безошибочно), затем фамилию (`-ов` / `-ова`). Готовая строка
«Уважаемая Елена Михайловна» уходит в промпт целиком, и менять её модели запрещено.

Фамилии, одинаковые у мужчин и женщин, — «Шмидт», «Коваль», «Черных», «Шевченко», «Бондарчук»,
«Арутюнян», «Дурново» — распознаются как неоднозначные, и пол по ним **не угадывается**:
обращение остаётся плейсхолдером, а пользователь получает предупреждение и поле выбора вручную.
Если пол определён по фамилии, а не по отчеству, ответ тоже помечается «проверьте обращение».

Имя и отчество для обращения — отдельное поле формы. Из инициалов «Е.М.» «Елена Михайловна»
не выводится ни кодом, ни моделью, ни человеком: во входящем письме этих данных просто нет.

#### Предупреждения вместо тихих плейсхолдеров

`POST /api/letters/reply` возвращает третье поле — `warnings`, и фронт печатает его над ответом.
Туда попадает всё, что осталось незаполненным не по вине модели: пустая карточка организации,
отсутствующий подписант или контактное лицо, неуказанный адресат, неопределённое обращение.
Без этого списка пользователь узнавал о проблеме, только вычитывая готовое письмо до конца.

### Что анонимизируется, а что нет

| Что уходит в GigaChat | Анонимизируется |
|---|---|
| Текст заявки → `ApplicationReviewAgent` | **Да**: docx чистится внутри файла, pdf — построчно после извлечения |
| Комментарий к загруженной заявке | **Да** |
| Реплика пользователя в чате → `ConsultingAgent` | **Да** |
| Текст входящего письма (`.docx`, `.pdf`, вставленный) → `LetterAgent` | **Да**, построчно пачкой |
| Указание «что ответить» | **Да** |
| Текст документа базы знаний → `ManualParserAgent` | **Нет**, уходит как есть |
| Содержимое таблиц в `query_dataset` | **Нет**: в модель уходит посчитанное число, а не строки |
| Карточка организации и подпись | **Нет**, уходит как есть |
| Адресат письма и обращение | **Нет**, уходит как есть |
| Шаблон ответа | **Нет**, уходит как есть |

Ответы агентов деанонимизируются обратно. Документ базы знаний — публичный и общий для всех чатов,
`sessionId` для него нет, так что его анонимизация не предполагалась вовсе.

**Почему три последние строки — «нет».** Это осознанное решение, а не упущение. Обезличивание
работает на границе с моделью и заменяет ПДн тегами `[EMAIL_0001]`. Для чужих данных это
правильно, а для своих — ломает задачу: если и наша почта, и почта отправителя приходят в модель
одинаковыми тегами, различить их нечем, и в блок «Контактное лицо» уезжает чужой адрес. Ровно так
и происходило до появления карточки.

Все три блока объединяет одно: их **вводит сам пользователь для того, чтобы они попали в письмо**.
Карточка организации и шаблон — собственные данные учреждения; адресат — должностное лицо, чьи
должность и фамилия и так стоят на бланке официальной переписки. Текст же самого входящего письма
обезличивается по-прежнему, и это главный источник чужих ПДн.

Ключ сессии определяет область видимости карты замен: для чата это `chatId` (живёт вместе с чатом),
для письма — разовый `letter:{userId}:{guid}`. Карта в любом случае истекает через 24 часа.

**Хранится всё в исходном виде.** И заявка в S3, и переписка в Valkey лежат с настоящими
персональными данными. Обезличивание применяется на лету, ровно на границе с моделью, и его
результат никуда не сохраняется. Раньше рядом с каждым сообщением лежала вторая, анонимизированная
копия текста — от неё отказались: две копии одного текста расходятся при любой правке, а история
для модели всё равно собирается заново на каждом запросе.

#### Как это не превращается в бутылочное горлышко

Обезличивание — синхронный сетевой вызов перед каждым обращением к модели, и на разборе заявки
их сотни. Поэтому:

- запросы длиннее `ANONYMIZER_MAX_REQUEST_CHARS` (8000) режутся по границе предложения и уходят
  параллельно, результат склеивается обратно;
- пакетная анонимизация истории (`AnonymizeBatchAsync`) собирает сообщения в пачки того же размера
  и отправляет пачки **одновременно**, а не по очереди;
- одновременных запросов к сервису не больше `ANONYMIZER_MAX_PARALLEL` (4) — `AnonymizeThrottle`
  держит семафор. Без него параллелизм упирался в GIL питона и делал только хуже.

Практическое следствие для истории диалога: перед отправкой в `ConsultingAgent` последние
15 сообщений обезличиваются пакетно. Теги при этом выдаются заново на каждый запрос, так что один
и тот же человек может получить `[PER_0001]` в одном запросе и `[PER_0007]` в следующем.
На деанонимизацию ответа это не влияет — каждый тег остаётся в карте сессии, — но карта растёт
с числом запросов, и модель видит один и тот же ключ по-разному между ходами. Если это начнёт
мешать, лечится обратным индексом «оригинал → тег» в `AnonymizeClient`.

### Расход токенов

Каждый вызов модели проходит через `ITokenMeter` и попадает в `token_usage`: операция, модель,
токены промпта и ответа, число вызовов инструментов, длительность, флаги `Partial` и `Failed`.
Операции разведены по смыслу — `Consulting`, `ManualParse`, `Letter`, `Embedding` и пять стадий
разбора заявки (`ReviewSection`, `ReviewCriteria`, `ReviewCoverage`, `ReviewMemo`,
`ReviewNarration`), так что видно, на что именно ушли лимиты.

Параллельно `BalanceProbe` снимает баланс GigaChat до и после операции и пишет разницу. Если
эндпоинт баланса недоступен, проба **выключается до перезапуска** и больше не дёргается — иначе
каждый вызов модели тащил бы за собой два заведомо провальных запроса.

Раздел «Токены» показывает сводку за 30 дней по умолчанию (максимум — год). Чистить журнал может
только `Rector`.

Пишутся через `ILogger` в stdout, читаются через `docker compose logs -f chatnode`.

| Уровень | Что попадает |
|---|---|
| `Debug` | Пошаговая работа инструментов: заметки агента, индексация документа, поиск, запросы к таблицам, расход токенов |
| `Information` | Вехи операции: старт разбора, критерии подняты, фрагмент проверен, итоговый балл |
| `Warning` | Деградации и повторы: ретрай GigaChat, урезание запроса, обрезка текста документа, Valkey не ответил |
| `Error` | Отказ внешнего сервиса: авторизация в GigaChat не прошла, TLS не сошёлся |

**В каждой записи по работе агента есть `chatId`**, у разбора документа — `manualId`. Без этого
разобрать по логам, что происходило, невозможно: параллельных разборов может идти несколько.

```
info: ChatNode.Infrastructure.AI.Agents.ApplicationReviewAgent[0]
      Разбор заявки 3f2a…: фрагмент 4/11 "Календарный план" (3820 симв., сводка=1240 симв.)
warn: ChatNode.Infrastructure.AI.Policy.GigaChatRetry[0]
      GigaChat: операция ответ консультанта не удалась (HTTP 429), попытка 2/2 через 5 с
```

Категория `ChatNode.Infrastructure.AI` включена на `Debug`, всё остальное — на `Information`.
Крутится переменной `LOG_LEVEL_AGENT`: поставьте `Information`, если пошаговая трасса инструментов
мешает читать.

## Конфигурация

Внутри контейнера конфиг ASP.NET Core берётся **только из переменных окружения** —
`ASPNETCORE_ENVIRONMENT=Production`, а `appsettings.Development.json` в этом режиме не читается.
`docker-compose.yml` разворачивает человекочитаемые имена из `.env` в имена секций .NET
(`GIGACHAT_SECTION_CHARS` → `GigaChat__ApplicationSectionChars`). У каждой необязательной переменной
есть значение по умолчанию в самом compose-файле.

### Обязательные

Все пять объявлены через `:?` — без любой из них compose не стартует.

| Переменная | Назначение |
|---|---|
| `GIGACHAT_AUTHORIZATION_KEY` | Ключ авторизации GigaChat. Без него **всё AI-поведение падает в рантайме, а не на старте** |
| `JWT_SECRET_KEY` | Ключ подписи JWT, минимум 32 байта (HS256). Проверяется на старте, короткий ключ роняет приложение |
| `POSTGRES_PASSWORD` | Пароль к базе |
| `STAFF_RECTOR_PASSWORD` | Пароль проректора |
| `STAFF_COORDINATOR_PASSWORD` | Пароль координатора |

### Служебные аккаунты

Проректор и координатор заводятся в PostgreSQL при старте из секции `StaffAccounts`. Пароль в `.env`
задаётся **открытым текстом** и хешируется PBKDF2-SHA256 (210 000 итераций, случайная соль) при
первой записи в базу — в открытом виде он в базу не попадает.

Дальше **источник истины — база, а не `.env`**: аккаунты из конфигурации создаются один раз и при
последующих запусках не перезаписываются. Иначе смена пароля через интерфейс молча откатывалась бы
при каждом перезапуске. Чтобы сбросить пароль забытого аккаунта, удалите его строку в
`user_accounts` — при следующем старте он создастся заново из `.env`.

| Переменная | По умолчанию |
|---|---|
| `STAFF_RECTOR_LOGIN` | `prorektor` |
| `STAFF_COORDINATOR_LOGIN` | `koordinator` |
| `STAFF_RECTOR_NAME` / `STAFF_COORDINATOR_NAME` | `Проректор` / `Координатор` |
| `STAFF_RECTOR_EMAIL` / `STAFF_COORDINATOR_EMAIL` | `prorektor@example.ru` / `koordinator@example.ru` |
| `STAFF_RECTOR_ID` / `STAFF_COORDINATOR_ID` | фиксированные GUID из compose |

### Самостоятельная регистрация

В модалке входа есть вкладка «Регистрация»: логин, имя, пароль и необязательная почта. Она создаёт
учётку с ролью `User` и сразу логинит. Прав это не добавляет — `User` может ровно то же, что гость,
разница только в том, что учётка и её чаты не истекают через сутки. Роль в запрос не передаётся и
подделать её нельзя: `RegisterAsync` проставляет `UserRole.User` сама.

Требования — логин от 3 символов из латиницы, цифр, точки, дефиса и подчёркивания; пароль
от 8 символов. Хешируется тем же PBKDF2, что и у служебных учёток.

### Ограничения на загрузку

| Переменная | По умолчанию | Комментарий |
|---|---|---|
| `MANUAL_STAFF_MAX_FILE_SIZE_BYTES` | `10485760` (10 МБ) | Лимит документа базы знаний для `Rector` и `Coordinator` |
| `MANUAL_MAX_FILE_SIZE_BYTES` | `262144` (256 КБ) | Лимит для всех остальных. **Сейчас недостижим**: загрузка в базу знаний закрыта для не-staff |
| `MANUAL_MAX_TEXT_CHARS` | `400000` | Потолок текста после извлечения. Всё сверх обрезается по границе строки с записью в лог |

Документ режется на части и целиком прогоняется через модель, поэтому большой файл — это минуты
работы и заметный расход лимитов GigaChat. Двухуровневый лимит по размеру файла остался с тех пор,
когда документ мог загрузить любой зарегистрированный пользователь; механизм в коде живой
и заработает, если загрузку снова откроют шире.

Лимит по размеру файла и лимит по символам решают разные задачи. 10 МБ `.xlsx` — это нормальная
выгрузка мониторинга, из которой в текст пойдёт разве что markdown-рендер таблицы, а 10 МБ `.pdf`
может развернуться в миллионы символов текста. Первый ограничивает трафик и память, второй — счёт
за модель.

Лимит на вложения (заявки `.docx`, письма `.docx` и `.pdf`) — **50 МБ**, задан константой
`UploadLimits.MaxDocxBytes`.
Потолок самого HTTP-запроса — **64 МБ** (`UploadLimits.MaxRequestBytes`), он выставляется
в `KestrelServerOptions` и `FormOptions` и совпадает с `client_max_body_size` в `nginx.conf`.
Порядок важен: если потолок запроса окажется ниже лимита валидатора, крупный файл получит голый
`413` от Kestrel вместо понятного сообщения об ошибке.

## Локальный запуск без Docker

Нужны .NET 10 SDK, Node 22+, Python 3.11+ и поднятые PostgreSQL **с расширением pgvector**, Valkey
и SeaweedFS на `localhost`. Локальные значения по умолчанию уже лежат
в `ChatNode/appsettings.Development.json`, там же служебные учётки `prorektor` / `prorektor`
и `koordinator` / `koordinator`.

```powershell
dotnet build AIAgentSberHakaton.sln
dotnet run --project ChatNode                 # http://localhost:5064, Scalar UI на /scalar
```

Ключ GigaChat в `appsettings` намеренно отсутствует — кладите его в user secrets:

```powershell
dotnet user-secrets --project ChatNode set "GigaChat:AuthorizationKey" "<ключ>"
```

Фронт:

```powershell
cd frontend
npm ci
npm run dev                                   # http://127.0.0.1:5173
```

Дев-сервер Vite проксирует `/api` и `/chat-hub` на `http://localhost:5064`, так что CORS не нужен
и здесь. Другой адрес бэкенда задаётся переменной `VITE_API_TARGET`.

Анонимайзер:

```powershell
pip install -r AnonimyzeService/requirements.txt
python AnonimyzeService/main.py
```

Удобнее всего гибридный вариант — инфраструктуру поднять в Docker, а `ChatNode` и фронт запускать
из IDE:

```powershell
docker compose up -d valkey postgres seaweedfs seaweedfs-init anonymizer
dotnet run --project ChatNode
```

Порты `5432`, `6379`, `8333`, `50051` проброшены наружу, поэтому `appsettings.Development.json`
с его `localhost` заработает без правок — и база при этом будет с pgvector.

### Как собирать проект

Только `dotnet build` или `dotnet publish`. **Никогда не проверяйте сборку через
`dotnet msbuild -t:Compile`**: цель `PrepareResources` висит на `Build`, а не на `CompileDependsOn`,
поэтому `-t:Compile` соберёт сборку с нулём встроенных ресурсов. Компилируется чисто, а в рантайме
падает на `Embedded resource 'ChatNode.Resources.russian_ca.cer' not found`.

Если `dotnet build` падает из-за того, что запущенное приложение держит `ChatNode.exe` — остановите
приложение или соберите в отдельный каталог через `-o`.

Тестового проекта в репозитории нет, `dotnet test` ничего не найдёт. Проверка изменений — прогон
в Docker (`docker compose up -d --build`) и ручной сценарий через интерфейс либо Scalar UI.
Фронт проверяется `npm run typecheck`.

### Миграции

Схема накатывается автоматически на старте. Новая миграция добавляется так:

```powershell
dotnet ef migrations add <Name> --project ChatNode --output-dir Infrastructure/Database/Migrations
```

## Справочник API

Всё, кроме `/api/auth/guest`, `/api/auth/login`, `/api/auth/register` и `/api/auth/refresh`,
требует JWT.

### Аутентификация

| Метод | Путь | Доступ | Описание |
|---|---|---|---|
| `POST` | `/api/auth/guest` | — | Гостевая пара токенов |
| `POST` | `/api/auth/register` | — | Регистрация: создаёт учётку с ролью `User` и сразу отдаёт пару токенов |
| `POST` | `/api/auth/login` | — | Вход по логину и паролю |
| `POST` | `/api/auth/refresh` | — | Обновление пары по refresh-токену |
| `GET` | `/api/auth/ws-ticket` | JWT | Одноразовый тикет для WebSocket (TTL 30 с) |

Роль в `/api/auth/register` не принимается: она всегда `User`. Повысить её может только проректор
через `/api/accounts`.

### База знаний

| Метод | Путь | Доступ | Описание |
|---|---|---|---|
| `POST` | `/api/manuals/upload` | `Rector`, `Coordinator` | Приём документа в очередь разбора, `202` (`multipart`: `Title`, `File` — `.md`, `.txt`, `.docx`, `.pdf`, `.csv`, `.xlsx`, `Scope` — `Staff` по умолчанию или `Public`) |
| `GET` | `/api/manuals` | JWT | Список документов со статусом разбора: staff видит оба списка, остальные — только общий |
| `GET` | `/api/manuals/{manualId}` | JWT | Статус разбора одного документа; служебный документ не-staff получает `404` |

Удаляется документ через реестр файлов: `DELETE /api/documents/{documentId}` по исходному файлу.
Вместе с ним каскадом уходят его части, эмбеддинги и таблицы.

Отдельного API у таблиц нет: они существуют только для агентов (`list_datasets`, `query_dataset`).

### Чаты и заявки

| Метод | Путь | Доступ | Описание |
|---|---|---|---|
| `POST` | `/api/chat` | JWT | Создать чат |
| `GET` | `/api/chat?lastChatId=&limit=10` | JWT | Список чатов, курсорная пагинация (`limit` ≤ 100) |
| `POST` | `/api/chat/{chatId}/files` | JWT | Приём заявки в очередь разбора, `202` (`multipart`: `File` — `.docx` или `.pdf`, `ManualId`, `Content`, `ContestKind`) |
| `DELETE` | `/api/chat/{chatId}` | JWT | Удалить чат вместе с файлами, находками и разборами |
| `GET` | `/api/chat/{chatId}/messages/{messageId}/review.docx` | JWT | Выгрузка разбора в `.docx` |

`ContestKind` — `Individual` (по умолчанию), `University`, `Nonprofit`. От него зависит, какие
критерии оценки агент поднимает из документа: у конкурсов для физлиц, вузов и НКО они разные.

Выгрузка разбора — сухой документ: заголовок, дата и содержание. Ни бланка с исходящим номером, ни
блока подписи с должностью и строкой исполнителя там нет: это результат автоматической проверки,
а не письмо за подписью, и оформлять его как официальный документ вводило бы в заблуждение.

### Файлы

| Метод | Путь | Доступ | Описание |
|---|---|---|---|
| `GET` | `/api/documents?kind=&limit=50&offset=0` | `Rector`, `Coordinator` | Реестр со статусом разбора по всем пользователям |
| `GET` | `/api/documents/{documentId}/content` | владелец или staff | Скачать файл |
| `DELETE` | `/api/documents/{documentId}` | владелец или staff | Удалить файл из хранилища и реестра |
| `GET` | `/api/reviews/active` | владелец | Разборы, идущие прямо сейчас: для восстановления статуса после перезагрузки |

Реестр и скачивание разделены намеренно. **Реестр** — служебный, он показывает чужие заявки
с персданными и закрыт от заявителей целиком. **Скачивание** — по владельцу: свою заявку
пользователь качает из чата, чужую не получит (`PermissionDenied` в `DocumentService.DownloadAsync`).

`kind` — `Manual`, `GrantApplication`, `GeneratedDocument`.

**Удаление** идёт по владельцу так же, как скачивание, и чистит всё, что тянется за файлом: объект
в S3, запись в реестре, а для заявки — ещё и сохранённый разбор с критериями. Файл базы знаний
удаляется вместе с самим документом: его разделы, эмбеддинги и таблицы без исходника не нужны.

Пока по файлу идёт работа — заявка в разборе, документ в стадии `Queued`/`Parsing` — удаление
отклоняется с `400`, иначе воркер оборвался бы на середине. Сообщения чата со ссылкой на удалённую
заявку остаются, но скачать по ним уже нечего; об этом предупреждает подтверждение в UI.

| Метод хаба | Описание |
|---|---|
| `CreateChat` | Создать чат (обычный или служебный) |
| `GetChatList(lastChatId, limit, kind)` | Список чатов; `kind` — `Grant` или `Staff` |
| `GetMessages(chatId, lastMessageId, limit)` | История сообщений |

`GetMessages` возвращает у каждого сообщения необязательный блок `file` (`documentId`, `fileName`,
`reviewMessageId`) — из него фронт рисует виджет вложения. Поэтому вложение переживает
перезагрузку: оно часть сообщения, а не состояние страницы.

Клиентские события:

| Событие | Полезная нагрузка |
|---|---|
| `AiStatusUpdate` | `chatId`, `status` — прогресс агента |
| `FileStatusChanged` | `fileName`, `status` (`Queued` / `Reviewing` / `Reviewed` / `Failed`) |
| `ReviewReady` | `chatId`, `documentId`, `messageId`, `content` |
| `ReviewFailed` | `chatId`, `fileName`, `messageId`, `reason` |
| `ManualStatus` | `manualId`, `title`, `stage` (`Queued` / `Parsing` / `Ready` / `Partial` / `Failed`), `totalChunks`, `processedChunks`, `failedChunks`, `detail`, `gaps` |

`chatId` в `AiStatusUpdate` и `documentId` в `ReviewReady` нужны для адресации: события летят
в группу пользователя, а не чата. Без них статус показывался бы в любом открытом чате, а кнопку
«Разбор» некуда было бы привязать при нескольких заявках в одном чате.

### Две схемы аутентификации

REST работает на обычном JWT Bearer. SignalR заголовки отправить не может, поэтому у хаба своя схема
`WebSocketScheme`: клиент с JWT дёргает `GET /api/auth/ws-ticket`, получает одноразовый тикет с TTL
30 секунд и подключается на `/chat-hub?ticket={guid}`. Каждое соединение вступает в группу
`user:{userId}` — туда и приходят статусы агента и готовые разборы, в том числе от фонового воркера.

### Ошибки

Все доменные исключения приводятся к `ProblemDetails` в `DomainExceptionHandler`:

| Код | Когда |
|---|---|
| `400` | Битый документ или неверный запрос |
| `403` | Отказ в доступе |
| `404` | Не найдено |
| `429` | Лимит GigaChat |
| `502` | Прочие отказы GigaChat |
| `503` | Анонимайзер недоступен |

Фронт достаёт из ответа `errors`, `detail` или `title` — в таком порядке.

## Грабли

**PostgreSQL нужен с pgvector.** Обычный `postgres:17-alpine` не подойдёт: миграция
`ManualPartsPgvector` создаёт расширение `vector`, колонку `vector(1024)` и HNSW-индекс по косинусу.
В compose стоит `pgvector/pgvector:pg17`.

**Смена модели эмбеддингов теперь ломает не индексы, а миграцию.** Размерность зашита в двух
местах: `GIGACHAT_EMBEDDING_DIM` и `ManualPartConfiguration.EmbeddingDimensions` (обе `1024`).
Поменять одну переменную окружения недостаточно — понадобится новая миграция, меняющая тип колонки,
и переразбор или пересчёт эмбеддингов. Молчаливой рассинхронизации, как было с `FT.CREATE`, больше
нет: несовпадение размерности вернёт ошибку из PostgreSQL.

**Модуль поиска в Valkey больше не нужен.** Код не выполняет ни `FT.CREATE`, ни `FT.SEARCH` —
единственное упоминание `FT.*` осталось в `ValkeyIndexInitializer`, который сносит индексы прошлых
версий и молча проглатывает `unknown command`. Образ `valkey/valkey-bundle` в compose оставлен,
но по этой причине его можно и заменить.

**Старые эмбеддинги переносятся сами.** `EmbeddingBackfill` при старте пачками по 200 заполняет
`EmbeddingVector` из исторической колонки `bytea`. Переразбирать документы после обновления
не нужно; в логах об этом будет одна строка `Векторы частей перенесены в pgvector`.

**`query_dataset` считает в PostgreSQL, а не в памяти.** Фильтрация, агрегация и группировка идут
одним запросом по `jsonb`; в .NET приезжают только итоговые числа и группы. Имена колонок
подставляются параметрами (`v ->> @p1`), так что подставить туда SQL нельзя даже теоретически.
Числа нормализуются на стороне базы тем же набором правил, что и в `DatasetNumber`: убираются
пробелы — обычный, неразрывный и узкий неразрывный, — знак процента, запятая становится точкой.
Правила обязаны совпадать: тип колонки определяет C# при загрузке, а считает потом SQL, и если
они разойдутся, колонка будет числовой, а сумма — нулевой.

Индекса по ключам `jsonb` нет: запрос упирается в `IX_dataset_rows_DatasetId` и дальше линейно
идёт по строкам таблицы. На потолке в 50 000 строк это доли секунды. Если таблицы вырастут
на порядок, добавляйте индекс выражения под конкретную колонку — общего индекса, который ускорит
`v ->> 'любая колонка'`, не существует.

**Бакет создаётся отдельным контейнером.** SeaweedFS не создаёт бакет сам при первом `PUT`, поэтому
`seaweedfs-init` дожидается S3-порта и делает `PUT /{bucket}`. Если переименовали `S3_BUCKET` —
нужен повторный `docker compose up seaweedfs-init`.

**Порт `5064` торчит наружу на всех интерфейсах.** В отличие от `valkey`, `postgres`, `seaweedfs`
и `anonymizer`, привязанных к `127.0.0.1`, сервис `chatnode` публикуется без привязки к адресу.
Это прямой доступ к API в обход nginx с его `client_max_body_size`. Для публичного развёртывания
стоит либо привязать его к `127.0.0.1`, либо убрать проброс совсем и ходить только через `web`.

**`UseHttpsRedirection` включается только в Development.** HTTPS-порт не настроен, поэтому
в Development в логах будет предупреждение `Failed to determine the https port for redirect`.
Запросы при этом проходят; TLS терминируйте на внешнем прокси.

**Ограничение — размер промпта, а не качество модели.** Русский текст стоит GigaChat примерно один
токен на 3 символа, и в каждый запрос уезжает системный промпт плюс полная JSON-схема всех
инструментов — причём заново на каждом витке цикла вызовов, тогда как текст фрагмента отправляется
один раз. Окно забивают **накопленные результаты вызовов инструментов**, а не входной текст: каждый
вызов дописывает найденные части документа и находки обратно в тот же диалог. Поэтому при `413`
уменьшать входной фрагмент обычно бесполезно — сначала посчитайте, сколько возвращают инструменты.
По той же причине разбору базы знаний выдаются только три инструмента, а оглавление и выдача
`list_datasets` урезаны по длине.

Диагностика по логам: если в них появились записи `не влез -> урезаю вызовы инструментов`, снижайте
`GIGACHAT_SECTION_TOOL_CALLS`, а если и это не помогло — `GIGACHAT_SECTION_CHARS` до 3000.
Записи вида `Методичка …: поиск "…" -> N частей, M симв.` печатают суммарный размер выдачи поиска
по документу — это самая дорогая позиция в цикле, и при разборе `413` смотреть надо в первую очередь
на неё. Обе видны при `LOG_LEVEL_AGENT=Debug`, который стоит по умолчанию.

**Данные в Valkey живут сутки.** Чаты, сообщения и находки истекают по `EXPIRATION_*`. Разборы,
документы базы знаний, таблицы, поручения, карточка организации, журнал токенов и учётки лежат
в PostgreSQL и не истекают. Если чат исчез, а разбор остался в разделе «Файлы» — это ожидаемое
поведение, а не потеря данных.
