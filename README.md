# Грантовый консультант

RAG-ассистент для работы с грантовыми заявками. Собран под хакатон Сбера, работает на GigaChat.

Проректор загружает **методичку** — положение о конкурсе в формате `.md`. Она разбирается на части и
индексируется в Valkey как векторное хранилище. Дальше с этой методичкой можно работать четырьмя
способами:

- **Спросить.** Консультант отвечает строго по методичке, а не по своим знаниям.
- **Проверить заявку.** Загружаете `.docx` — получаете разбор: балл по каждому критерию, что
  нарушено, что требует уточнения, каких разделов не хватает. Отдельным блоком — расхождения в смете,
  посчитанные кодом, а не моделью.
- **Ответить на письмо.** По шаблону, с автоматическим извлечением поручений из текста.
- **Вести поручения.** Список задач с исполнителями, сроками и статусами.

Тяжёлая работа идёт в фоне. Файл встаёт в очередь, воркер забирает его и присылает результат через
SignalR — закрытая вкладка проверку не отменяет.

## Запуск за пять минут

Нужен Docker Desktop или Docker Engine с Compose v2.

**1. Заведите `.env`:**

```powershell
copy .env.example .env
```

**2. Заполните три обязательных ключа** — без них `docker compose` откажется стартовать:

```dotenv
GIGACHAT_AUTHORIZATION_KEY=<ключ авторизации GigaChat в base64>
JWT_SECRET_KEY=<случайная строка от 32 символов>
POSTGRES_PASSWORD=<пароль к базе>
```

Пароли служебных учёток в `.env.example` уже проставлены (`prorektor` / `koordinator`), так что для
локального прогона этих трёх строк достаточно.

Секрет JWT удобно сгенерировать так:

```powershell
[Convert]::ToBase64String((1..48 | % { Get-Random -Max 256 }))
```

**3. Поднимите:**

```powershell
docker compose up -d --build
docker compose logs -f chatnode
```

Первая сборка долгая — образ анонимайзера тянет с Hugging Face NER-модель на 1–2 ГБ и запекает её
внутрь. Это происходит один раз; дальше старт быстрый и сети не требует.

**4. Проверьте, что поднялось:**

| Что | Адрес |
|---|---|
| **Интерфейс** — сюда и заходить | http://localhost:8080 (вход `prorektor` / `prorektor`) |
| Scalar UI | http://localhost:5064/scalar (только при `ASPNETCORE_ENVIRONMENT=Development`) |
| OpenAPI | http://localhost:5064/openapi/v1.json (там же) |
| SeaweedFS filer | http://localhost:8888 |

`docker compose ps` должен показать все сервисы в `healthy`/`running`, а `seaweedfs-init` —
в `exited (0)`: это одноразовый контейнер, который создаёт бакет и завершается.

**5. Пройдите сценарий целиком:**

1. Войдите проректором, загрузите методичку `.md` в панели слева и дождитесь стадии `Ready`.
2. Задайте по ней вопрос в чате — консультант ответит цитатами из неё.
3. Приложите к сообщению `.docx`-заявку и выберите тип конкурса. Разбор придёт в чат сам.
4. Загляните в «Поручения» и «Загруженные файлы».

Остановка и полная очистка данных:

```powershell
docker compose down       # остановить
docker compose down -v    # остановить и стереть тома
```

## Что внутри интерфейса

Пять разделов, доступ зависит от роли.

| Раздел | Путь | Кому | Что делает |
|---|---|---|---|
| Заявки | `/chat` | всем, включая гостей | Диалог с консультантом, загрузка `.docx` на проверку, скачивание заявки и разбора прямо из вложения в чате |
| Деловая переписка | `/letters` | `Rector` | Ответ на письмо по шаблону, извлечение поручений из текста |
| Поручения | `/assignments` | `Rector`, `Coordinator` | Список задач: исполнитель, срок, статус |
| Загруженные файлы | `/files` | `Rector`, `Coordinator` | Реестр загруженного, статус разбора, скачивание |
| Учётные записи | `/accounts` | `Rector` | Создание и удаление учёток, смена роли и пароля |

### Роли

| Роль | Как появляется | Права |
|---|---|---|
| `Guest` | Автоматически при первом заходе, живёт в Valkey с TTL | Чат и проверка заявок |
| `User` | Самостоятельная регистрация или заводит проректор | **Ровно те же, что у гостя** |
| `Coordinator` | Заводит проректор или seeder из `.env` | Плюс поручения, реестр файлов и загрузка методичек |
| `Rector` | Seeder из `.env`, дальше — из базы | Всё, включая учётки, письма и шаблоны писем |

Граница прав в системе ровно одна: `Rector` и `Coordinator` — служебные роли (staff). Всё, что не
относится к работе с собственной заявкой — реестр файлов, поручения, загрузка методичек, учётки,
письма, — доступно только им.

`Guest` и `User` по возможностям неразличимы. Регистрация ничего не открывает; она нужна, чтобы чаты
и разобранные заявки не пропали вместе с гостевой сессией и были доступны с другого устройства.

Себя разжаловать или удалить нельзя, последнего проректора удалить тоже нельзя — иначе управлять
учётками стало бы некому.

## Архитектура

Три сервиса и четыре хранилища, всё поднимается одним `docker compose`.

```
                  браузер
                     │
                  [ web ]  nginx: статика + прокси /api и /chat-hub
                     │
                [ chatnode ]  .NET 10: REST, SignalR, агенты, воркеры
                 ╱   │   │  ╲
        postgres  valkey  s3  [ anonymizer ]  Python: gRPC, вырезание ПДн
                                    │
                                GigaChat
```

### `ChatNode` — .NET 10, ASP.NET Core

REST API, SignalR-хаб, агенты, фоновые воркеры, работа с PostgreSQL, Valkey и S3. Слушает `8080`
в контейнере, наружу проброшен на `5064`.

Внутри одного проекта три слоя папками, у каждого свой DI-extension, вызываемый в `Program.cs`:
`Infrastructure` → `Application` → `Api`. `Domain` — отдельная библиотека с сущностями и интерфейсами
репозиториев, без зависимостей. Направление зависимостей Api → Application → Infrastructure → Domain,
но `Application` напрямую использует типы `Infrastructure`, так что это не строгий onion.

Четыре агента поверх GigaChat, все с function calling:

| Агент | Что делает |
|---|---|
| `ManualParserAgent` | Режет методичку на части и наполняет RAG-индекс |
| `ConsultingAgent` | Отвечает на вопросы по методичке, читает находки проверки заявки |
| `ApplicationReviewAgent` | Проверяет `.docx`-заявку по методичке и собирает разбор |
| `LetterAgent` | Готовит ответ на письмо по шаблону и вытаскивает из него поручения |

Эндпоинты GigaChat требуют российских корневых сертификатов: `Resources/*.cer` встроены в сборку
и подключаются ко всем HTTP-хендлерам GigaChat.

### `AnonimyzeService` — Python 3.11, gRPC

Убирает персональные данные из текста до того, как он уйдёт в GigaChat. Слушает `50051`.
Мультиязычная NER-модель `Wismut/nym-pii-multilingual` плюс regex с проверкой контрольных сумм для
ИНН и СНИЛС. Найденное заменяется тегами `[TYPE_XXXX]`, соответствие «тег → оригинал» кладётся
в Valkey под ключ `anon:{sessionId}` на 24 часа, чтобы ответ агента можно было деанонимизировать.

Модель **вшивается в образ на `docker build`** через `save_pretrained` в `/opt/models/pii-model`,
рантайму сеть и тома не нужны. Раньше она тянулась с Hugging Face при первом старте — без доступа
к HF контейнер не становился healthy, а `chatnode` ждёт его через `depends_on: service_healthy`,
то есть не поднималось вообще ничего.

Контракт лежит **в двух копиях**: `ChatNode/Protos/anonymize_service.proto` и
`AnonimyzeService/protos/anonymize_service.proto` — править нужно оба. C#-клиент генерируется
на сборке через `Grpc.Tools`, Python-стабы в `AnonimyzeService/generated/` закоммичены и после
правки proto перегенерируются руками (`grpcio-tools` нужен только для этого и в `requirements.txt`
намеренно не входит):

```powershell
pip install grpcio-tools
python -m grpc_tools.protoc -I AnonimyzeService/protos --python_out=AnonimyzeService/generated --grpc_python_out=AnonimyzeService/generated AnonimyzeService/protos/anonymize_service.proto
```

### `frontend` — React 19, Vite, TypeScript

SPA на React Router, SignalR-клиент, без UI-библиотек. Собирается в образ `web` и раздаётся
nginx-ом, он же проксирует `/api` и `/chat-hub` на `chatnode`. Всё живёт на одном origin, поэтому
CORS не нужен и в бэкенде не настроен.

### Инфраструктура

| Сервис | Зачем | Порт |
|---|---|---|
| `postgres` | Постоянные данные: аккаунты, методички, поручения, реестр файлов, разборы, шаблоны писем | `5432` |
| `valkey` | Кеш, векторные индексы, чаты и сообщения, очередь разбора. Нужен **модуль поиска** (`FT.CREATE`/`FT.SEARCH`) | `6379` |
| `seaweedfs` | S3-совместимое хранилище файлов | `8333` (S3), `8888` (filer), `9333` (master) |
| `seaweedfs-init` | Одноразовый контейнер: создаёт бакет и завершается | — |
| `anonymizer` | gRPC-сервис обезличивания | `50051` |
| `chatnode` | Бэкенд | `5064` → `8080` |
| `web` | nginx: фронт и прокси | `8080` → `80` |

### Что где лежит

Разделение не интуитивное, поэтому явно.

**PostgreSQL — источник истины.** Схема накатывается EF-миграциями автоматически при старте
`chatnode`, руками ничего запускать не нужно.

| Таблица | Что |
|---|---|
| `user_accounts` | Учётки с PBKDF2-хешами паролей |
| `manuals`, `manual_parts` | Методички и их разобранные части |
| `stored_documents` | Реестр загруженного: кто, в какой чат, какой файл, ключ в S3 |
| `assignments` | Поручения |
| `letter_templates` | Шаблоны ответов на письма |
| `application_reviews`, `application_review_criteria` | Сохранённые разборы заявок с баллами по критериям |

**Valkey — оперативное состояние с TTL.** Данные здесь **протухают через сутки** (настраивается
блоком `EXPIRATION_*`).

| Ключ | Что |
|---|---|
| `idx:manual_parts_v2` | Векторный индекс частей методички (HNSW, косинус) |
| `idx:pins` | Векторный индекс находок проверки |
| `manualpart:{manualId}:{partId}` | Кеш частей, прогревается из PostgreSQL по требованию |
| `pin:*` | Находки агента по текущей проверке |
| `anon:{sessionId}` | Карта «тег → оригинал» для деанонимизации, TTL 24 ч |
| `review:jobs` | Stream очереди разбора заявок, consumer group `reviewers` |
| `manual:jobs` | Stream очереди разбора методичек, consumer group `manual-parsers` |
| `review:status:{ownerId}` | Стадия разбора по каждому документу |
| чаты, сообщения, гости, ws-тикеты | Сообщения — Redis Stream, текст лежит как есть; у сообщения с вложением есть `DocumentId` и `FileName`. Гостевые аккаунты в базу не пишутся |

**S3 (SeaweedFS) — файлы.** Методички и загруженные заявки.

> **Важно.** В хранилище заявка кладётся **как есть, с исходными персданными**. Обезличивание живёт
> только на границе с моделью: копия для GigaChat чистится на лету и никуда не сохраняется.
> Следствие — в бакете лежат настоящие персональные данные, и доступ к нему нужно ограничивать
> соответственно. В compose порты SeaweedFS привязаны к `127.0.0.1`.

## Как это работает

### Загрузка методички

Запрос не ждёт разбора. `POST /api/manuals/upload` кладёт файл в S3, заводит запись в реестре
документов и ставит задачу в поток Valkey `manual:jobs`, после чего сразу отвечает `202` с
`manualId` и стадией `Queued`. Дальше работает `ManualParseWorker`: забирает задачу, качает файл
из S3 и запускает разбор. Зависшие задачи подбираются по `XPENDING` через 30 минут, максимум
две попытки.

`ManualParserAgent` режет файл на куски примерно по 4000 символов по структурным границам,
с перекрытием в 500 символов, и скармливает модели по одному — перекрытие идёт как «уже
обработанный» контекст. Модель вызывает `add_manual_part` и `add_manual_navigation_header`, из чего
и собирается RAG-индекс. Куски, которые упали или исчерпали бюджет вызовов, собираются в список и
проходят второй раз половинным размером: один сбойный кусок больше не роняет всю методичку.

Стадия разбора живёт в таблице `manuals` (`Stage`, `TotalChunks`, `ProcessedChunks`, `FailedChunks`,
`StatusDetail`) и параллельно уходит владельцу по SignalR событием `ManualStatus`:
`Queued` → `Parsing` (с прогрессом) → `Ready`, `Partial` или `Failed`.

`Partial` означает, что часть фрагментов в базу знаний не попала. В `StatusDetail` и в поле `gaps`
события перечислены их заголовки и причина — чтобы было видно, что именно осталось непроверяемым.
Если не разобрался ни один фрагмент, стадия `Failed`. Фронт держит методички в неготовых стадиях
под опросом раз в 7 секунд, показывает статус в панели слева и не даёт отправлять по ним заявки.

Части сохраняются в PostgreSQL, а их эмбеддинги — в Valkey под индексом `idx:manual_parts_v2`.
Кеш прогревается из базы по требованию, так что после `docker compose down -v` методички
не теряются: пересоздастся индекс, а не контент.

### Диалог

`ConsultingAgent` отвечает **только** по результатам KNN-поиска `search_in_manual` и обязан звать
`send_status_of_processing` перед каждым поиском, чтобы пользователь видел прогресс. Дополнительно
он получает read-only доступ к находкам проверки заявки в том же чате (`get_pins`, `search_pins`) —
так что после проверки можно спросить «а что было не так».

В историю сохраняются только текстовые ответы, результаты вызовов инструментов — нет. Системный
промпт поэтому явно требует искать заново, а не пересказывать собственный прошлый ответ.

### Проверка заявки: очередь

`POST /api/chat/{chatId}/files` **не проверяет заявку синхронно.** Он кладёт файл в S3, регистрирует
его в `stored_documents`, ставит задание в Valkey Stream `review:jobs` и отвечает `202` с глубиной
очереди. Разбор идёт в фоне, закрытая вкладка его не отменяет.

Сообщение о загрузке — не текст. В поток чата пишется только комментарий пользователя (часто
пустой), а сам файл живёт в полях `DocumentId` и `FileName` того же сообщения. Фронт рисует по ним
виджет вложения с кнопками «Заявка» и «Разбор»; вторая появляется, когда для этого `documentId`
находится сохранённый разбор. Раньше вместо этого в чат писалась строка «Загружена заявка
на проверку: …», из которой ничего нельзя было скачать.

`ReviewWorker` — `BackgroundService`, читающий стрим через consumer group `reviewers`. Задание
подтверждается (`XACK` + `XDEL`) только после успеха. Если воркер умер посреди работы, задание
зависает в pending-списке; через 10 минут простоя его подбирает `ReclaimAsync`, а после трёх попыток
оно снимается с очереди и пользователю в чат уходит сообщение о неудаче.

Ошибки делятся на постоянные и временные. `InvalidDocumentException`, `NotFoundException` и
`FileNotFoundException` — постоянные: повторять их бессмысленно, задание сразу снимается с очереди,
а пользователь получает причину. Остальное возвращается в очередь.

Перед разбором `RunApplicationReviewAsync` проверяет, что чат ещё существует. Проверка стоит
до первого обращения к модели намеренно: без неё разбор заявки из удалённого чата отрабатывал
целиком — минуты работы и полный расход лимитов GigaChat — и падал в самом конце, когда результат
уже некуда сохранять.

Исключения-«не найдено» живут в одном месте, `ChatNode.Application.Exceptions`. Раньше рядом
существовала вторая иерархия `ChatNode.Infrastructure.Exceptions` с одноимённым `NotFoundException`:
репозиторий бросал инфраструктурный, а воркер и обработчик HTTP-ошибок сопоставляли прикладной.
Типы разные, совпадение по `is` не срабатывало — задание считалось временной ошибкой и висело три
попытки, а REST отдавал `500` вместо `404`.

Прогресс пишется в `review:status:{ownerId}` и параллельно уходит в SignalR-группу пользователя,
поэтому раздел «Файлы» показывает стадию разбора даже после перезагрузки страницы.

### Проверка заявки: разбор

Файл забирается из S3 → ПДн вычищаются **прямо внутри docx** (ключ сессии = `chatId`) →
анонимизированная копия режется на секции → `ApplicationReviewAgent` идёт по ним **строго по одной**
→ результат деанонимизируется и добавляется в чат сообщением агента.

Порядок «сначала анонимизация, потом нарезка» не случаен, и параллелить фрагменты нельзя: контекст
фрагмента об остальном документе — это хранилище находок и накопительная сводка, и при конкурентной
обработке двенадцатый фрагмент прочитает и то и другое наполовину заполненными.

Фрагменты связаны накопительной сводкой: после каждого в неё сливается всё, что агент записал,
изменил или удалил, а следующий получает её хвост в промпте. Сводку ведёт код, инструментов для её
правки у модели нет — поэтому удалить находку она может, а «забыть» прочитанный раздел нет.

Отдельный проход `ExtractCriteriaAsync` вытаскивает из методички критерии оценки под выбранный тип
конкурса; их названия уходят в промпт каждой секции. Если критериев в методичке нет, извлечение
возвращает пусто и разбор деградирует до простого списка находок — критерии не выдумываются.

**Проход по секции не имеет права заявлять, что чего-то нет.** Он видит один фрагмент из многих,
и «бюджет не указан» почти всегда ложь: бюджет в соседнем фрагменте. Реальные пропуски ищет
`CheckCoverageAsync` — единственное место с обзором всего документа. Формулировки отсутствия
в находках принудительно понижаются до «проверить вручную».

Теги вида `[PER_0001]` в тексте — **не дефект заявки**: значение есть, оно просто скрыто
от проверяющего. Это зафиксировано и в промптах, и в коде.

### Баллы считает код, а не модель

Это ключевое решение всего разбора. Модель находит проблемы, но **не выставляет оценки**.

`ReviewConsolidator` сопоставляет находки с критериями и считает балл детерминированно:

| Вывод | Балл |
|---|---|
| Замечаний нет | максимум по критерию |
| Требует уточнения | `round(max × 0.7)`, но не ниже половины максимума |
| Нарушение | `round(max × 0.3)` |
| Раздел не найден | `0` |

Каждая находка сверх первой снимает ещё балл в пределах тех же границ. Дубли отсеиваются по первым
80 символам нормализованного текста.

После этого `ReviewNarration` отправляет модели уже посчитанный результат с единственной задачей —
объяснить его человеческим языком, по строке на критерий. Системный промпт прямо запрещает спорить
с выводом и менять балл. Собранный `ApplicationReviewResult` сохраняется в `application_reviews` /
`application_review_criteria`, а `ReviewRenderer` печатает его в markdown.

### Смету тоже считает код

`ApplicationNumbersAnalyzer` разбирает числовые разделы заявки без участия модели и проверяет:

- сумму строк сметы против заявленной общей суммы;
- **произведение цены на количество в каждой строке** против указанной суммы;
- плановые показатели против того, что просуммировано по разделам мероприятий и публикаций;
- обещания вида «не менее N» в формулировке цели против плановых значений;
- доли категорий расходов, запрошенную сумму на одного участника, долю софинансирования.

Найденные расхождения уходят в разбор отдельным блоком «Проверено расчётом» с явной пометкой, что
они посчитаны по документу, а не выведены моделью, и попадают в промпт `ReviewNarration` как
проверенные факты с требованием переносить числа дословно.

Строка сметы, где произведение не сходится с суммой, печатается как
`1 000 руб. × 5 = 5 000 руб. ≠ 50 000 руб.` — знак `≠` показывает, что равенство не выполняется.
Случай, когда общая сумма сходится, а отдельная строка внутри себя противоречива, ловится именно
здесь: проверки итога для него недостаточно.

### Письма

`LetterAgent` получает текст письма (из `.docx` или вставленный руками), намерение ответа и
необязательный шаблон. Шаблон уходит в модель как обязательная структура: она повторяет его блоки
и формулировки, подставляя данные из письма, а незаполненные плейсхолдеры перечисляет в конце под
заголовком «Требуется уточнить». Параллельно агент вытаскивает из письма поручения — они создаются
в разделе «Поручения» с источником `Letter`.

Шаблоны видит только их автор и, как и текст письма, они обезличиваются перед отправкой в модель:
в шаблоне может стоять блок подписи с фамилией.

### Что анонимизируется, а что нет

| Что уходит в GigaChat | Анонимизируется |
|---|---|
| Текст `.docx`-заявки → `ApplicationReviewAgent` | **Да**, перед нарезкой на секции |
| Комментарий к загруженной заявке | **Да** |
| Реплика пользователя в чате → `ConsultingAgent` | **Да** |
| Текст письма и шаблон ответа → `LetterAgent` | **Да** |
| Текст методички → `ManualParserAgent` | **Нет**, уходит как есть |

Ответы агентов деанонимизируются обратно. Методичка — документ публичный и общий для всех чатов,
`sessionId` для неё нет, так что её анонимизация не предполагалась вовсе.

Ключ сессии определяет область видимости карты замен: для чата это `chatId` (живёт вместе с чатом),
для письма — разовый `letter:{userId}:{guid}`. Карта в любом случае истекает через 24 часа.

**Хранится всё в исходном виде.** И заявка в S3, и переписка в Valkey лежат с настоящими
персональными данными. Обезличивание применяется на лету, ровно на границе с моделью, и его
результат никуда не сохраняется. Раньше рядом с каждым сообщением лежала вторая, анонимизированная
копия текста — от неё отказались: две копии одного текста расходятся при любой правке, а история
для модели всё равно собирается заново на каждом запросе.

Практическое следствие для истории диалога: перед отправкой в `ConsultingAgent` последние
15 сообщений обезличиваются пакетно через `AnonymizeBatchAsync`. Теги при этом выдаются заново
на каждый запрос, так что один и тот же человек может получить `[PER_0001]` в одном запросе
и `[PER_0007]` в следующем. На деанонимизацию ответа это не влияет — каждый тег остаётся в карте
сессии, — но карта растёт с числом запросов, и модель видит один и тот же ключ по-разному между
ходами. Если это начнёт мешать, лечится обратным индексом «оригинал → тег» в `AnonymizeClient`.

## Логи

Пишутся через `ILogger` в stdout, читаются через `docker compose logs -f chatnode`.

| Уровень | Что попадает |
|---|---|
| `Debug` | Пошаговая работа инструментов: заметки агента, индексация методички, поиск, расход токенов |
| `Information` | Вехи операции: старт разбора, критерии подняты, фрагмент проверен, итоговый балл |
| `Warning` | Деградации и повторы: ретрай GigaChat, урезание запроса, Valkey не ответил |
| `Error` | Отказ внешнего сервиса: авторизация в GigaChat не прошла, TLS не сошёлся |

**В каждой записи по работе агента есть `chatId`**, у разбора методички — `manualId`. Без этого
разобрать по логам, что происходило, невозможно: параллельных разборов может идти несколько.

```
info: ChatNode.Infrastructure.AI.Agents.ApplicationReviewAgent[0]
      Разбор заявки 3f2a…: фрагмент 4/11 "Календарный план" (3820 симв., сводка=1240 симв.)
warn: ChatNode.Infrastructure.AI.Policy.GigaChatRetry[0]
      GigaChat: операция ответ консультанта не удалась (HTTP 429), попытка 2/2 через 5 с
```

Категория `ChatNode.Infrastructure.AI` включена на `Debug`, всё остальное — на `Information`.
Крутится переменной `LOG_LEVEL_AGENT`: поставьте `Information`, если пошаговая трасса инструментов
мешает читать.

## Конфигурация

Внутри контейнера конфиг ASP.NET Core берётся **только из переменных окружения** —
`ASPNETCORE_ENVIRONMENT=Production`, а `appsettings.Development.json` в этом режиме не читается.
`docker-compose.yml` разворачивает человекочитаемые имена из `.env` в имена секций .NET
(`GIGACHAT_SECTION_CHARS` → `GigaChat__ApplicationSectionChars`). У каждой переменной есть значение
по умолчанию в самом compose-файле, так что `.env` с тремя обязательными ключами уже рабочий.

### Обязательные

| Переменная | Назначение |
|---|---|
| `GIGACHAT_AUTHORIZATION_KEY` | Ключ авторизации GigaChat. Без него **всё AI-поведение падает в рантайме, а не на старте** |
| `JWT_SECRET_KEY` | Ключ подписи JWT, минимум 32 байта (HS256). Проверяется на старте, короткий ключ роняет приложение |
| `POSTGRES_PASSWORD` | Пароль к базе |
| `STAFF_RECTOR_PASSWORD` | Пароль проректора (в `.env.example` заполнен) |
| `STAFF_COORDINATOR_PASSWORD` | Пароль координатора (в `.env.example` заполнен) |

### Служебные аккаунты

Проректор и координатор заводятся в PostgreSQL при старте из секции `StaffAccounts`. Пароль в `.env`
задаётся **открытым текстом** и хешируется PBKDF2-SHA256 (210 000 итераций, случайная соль) при
первой записи в базу — в открытом виде он в базу не попадает.

Дальше **источник истины — база, а не `.env`**: аккаунты из конфигурации создаются один раз и при
последующих запусках не перезаписываются. Иначе смена пароля через интерфейс молча откатывалась бы
при каждом перезапуске. Чтобы сбросить пароль забытого аккаунта, удалите его строку в
`user_accounts` — при следующем старте он создастся заново из `.env`.

| Переменная | По умолчанию |
|---|---|
| `STAFF_RECTOR_LOGIN` / `STAFF_RECTOR_PASSWORD` | `prorektor` / `prorektor` |
| `STAFF_COORDINATOR_LOGIN` / `STAFF_COORDINATOR_PASSWORD` | `koordinator` / `koordinator` |

### Самостоятельная регистрация

В модалке входа есть вкладка «Регистрация»: логин, имя, пароль и необязательная почта. Она создаёт
учётку с ролью `User` и сразу логинит. Прав это не добавляет — `User` может ровно то же, что гость,
разница только в том, что учётка и её чаты не истекают через сутки. Роль в запрос не передаётся и
подделать её нельзя: `RegisterAsync` проставляет `UserRole.User` сама.

Требования — логин от 3 символов из латиницы, цифр, точки, дефиса и подчёркивания; пароль
от 8 символов. Хешируется тем же PBKDF2, что и у служебных учёток.

### Ограничения на загрузку

| Переменная | По умолчанию | Комментарий |
|---|---|---|
| `MANUAL_STAFF_MAX_FILE_SIZE_BYTES` | `10485760` (10 МБ) | Лимит методички для `Rector` и `Coordinator` |
| `MANUAL_MAX_FILE_SIZE_BYTES` | `262144` (256 КБ) | Лимит для всех остальных. **Сейчас недостижим**: загрузка методичек закрыта для не-staff |

Методичка режется на части и целиком прогоняется через модель, поэтому большой файл — это минуты
работы и заметный расход лимитов GigaChat. Двухуровневый лимит остался с тех пор, когда методичку
мог загрузить любой зарегистрированный пользователь; механизм в коде живой и заработает, если
загрузку снова откроют шире.

Потолок самого HTTP-запроса — **64 МБ** (`UploadLimits.MaxRequestBytes`), он выставляется
в `KestrelServerOptions` и `FormOptions` и совпадает с `client_max_body_size` в `nginx.conf`.
Порядок важен: если потолок запроса окажется ниже лимита валидатора, крупный файл получит голый
`413` от Kestrel вместо понятного сообщения об ошибке.

`REDACT_TYPES` расширять стоит осторожно. Модель выдаёт 41 тип, а скрываются только те, что реально

в грантовой заявке это не персданные, а её содержание: сроки проекта, площадки, ссылки, опыт
команды. Когда их скрывали, номер пункта «5.» превращался в `[DATE_010B]`, а название конференции —
в `[COMPANY_NAME_0115]`, и агент честно помечал корректные разделы как дефектные.

### Что попадает в образы

Контекст сборки `chatnode` — корень репозитория, но `.dockerignore` устроен как «запретить всё,
потом разрешить `ChatNode/` и `Domain/`». Больше в образ не уходит ничего.

Контекст `anonymizer` — `AnonimyzeService/`, из него в образ попадают только `main.py`,
`requirements.txt` и `generated/`. `protos/` и локальный `.env` отрезаны, чтобы `load_dotenv()`
в контейнере не перекрывал переменные окружения из compose.

Контекст `web` — `frontend/`, собирается многостадийно: `node:22-alpine` собирает `dist`,
`nginx:1.27-alpine` его раздаёт.

Запас времени на healthcheck анонимайзера задаётся `ANONYMIZER_START_PERIOD`, по умолчанию `120s`.

## Локальный запуск без Docker

Нужны .NET 10 SDK, Node 22+, Python 3.11+ и поднятые PostgreSQL, Valkey (с модулем поиска)
и SeaweedFS на `localhost`. Локальные значения по умолчанию уже лежат
в `ChatNode/appsettings.Development.json`.

```powershell
dotnet build AIAgentSberHakaton.sln
dotnet run --project ChatNode                 # http://localhost:5064, Scalar UI на /scalar
```

Ключ GigaChat в `appsettings` намеренно отсутствует — кладите его в user secrets:

```powershell
dotnet user-secrets --project ChatNode set "GigaChat:AuthorizationKey" "<ключ>"
```

Фронт:

```powershell
cd frontend
npm ci
npm run dev                                   # http://127.0.0.1:5173
```

Дев-сервер Vite проксирует `/api` и `/chat-hub` на `http://localhost:5064`, так что CORS не нужен
и здесь. Другой адрес бэкенда задаётся переменной `VITE_API_TARGET`.

Анонимайзер:

```powershell
pip install -r AnonimyzeService/requirements.txt
python AnonimyzeService/main.py
```

Удобнее всего гибридный вариант — инфраструктуру поднять в Docker, а `ChatNode` и фронт запускать
из IDE:

```powershell
docker compose up -d valkey postgres seaweedfs seaweedfs-init anonymizer
dotnet run --project ChatNode
```

Порты `5432`, `6379`, `8333`, `50051` проброшены наружу, поэтому `appsettings.Development.json`
с его `localhost` заработает без правок.

### Как собирать проект

Только `dotnet build` или `dotnet publish`. **Никогда не проверяйте сборку через
`dotnet msbuild -t:Compile`**: цель `PrepareResources` висит на `Build`, а не на `CompileDependsOn`,
поэтому `-t:Compile` соберёт сборку с нулём встроенных ресурсов. Компилируется чисто, а в рантайме
падает на `Embedded resource 'ChatNode.Resources.russian_ca.cer' not found`.

Если `dotnet build` падает из-за того, что запущенное приложение держит `ChatNode.exe` — остановите
приложение или соберите в отдельный каталог через `-o`.

Тестового проекта в репозитории нет, `dotnet test` ничего не найдёт. Проверка изменений — прогон
в Docker (`docker compose up -d --build`) и ручной сценарий через интерфейс либо Scalar UI.
Фронт проверяется `npm run typecheck`.

```powershell
dotnet ef migrations add <Name> --project ChatNode --output-dir Infrastructure/Database/Migrations
```

## Справочник API

Всё, кроме `/api/auth/guest`, `/api/auth/login` и `/api/auth/refresh`, требует JWT.

### Аутентификация

| Метод | Путь | Доступ | Описание |
|---|---|---|---|
| `POST` | `/api/auth/guest` | — | Гостевая пара токенов |
| `POST` | `/api/auth/register` | — | Регистрация: создаёт учётку с ролью `User` и сразу отдаёт пару токенов |
| `POST` | `/api/auth/login` | — | Вход по логину и паролю |
| `POST` | `/api/auth/refresh` | — | Обновление пары по refresh-токену |
| `GET` | `/api/auth/ws-ticket` | JWT | Одноразовый тикет для WebSocket (TTL 30 с) |

Роль в `/api/auth/register` не принимается: она всегда `User`. Повысить её может только проректор
через `/api/accounts`.

### Методички

| Метод | Путь | Доступ | Описание |
|---|---|---|---|
| `POST` | `/api/manuals/upload` | `Rector`, `Coordinator` | Приём методички в очередь разбора, `202` (`multipart`: `Title`, `File` — `.md`) |
| `GET` | `/api/manuals` | JWT | Список методичек со статусом разбора |
| `GET` | `/api/manuals/{manualId}` | JWT | Статус разбора одной методички |

Удаляется методичка через реестр файлов: `DELETE /api/documents/{documentId}` по её `.md`.

### Чаты и заявки

| Метод | Путь | Доступ | Описание |
|---|---|---|---|
| `POST` | `/api/chat` | JWT | Создать чат |
| `GET` | `/api/chat?lastChatId=&limit=10` | JWT | Список чатов, курсорная пагинация |
| `POST` | `/api/chat/{chatId}/files` | JWT | Приём заявки в очередь разбора, `202` (`multipart`: `File` — `.docx`, `ManualId`, `Content`, `ContestKind`) |
| `DELETE` | `/api/chat/{chatId}` | JWT | Удалить чат вместе с файлами, находками и разборами |
| `GET` | `/api/chat/{chatId}/messages/{messageId}/review.docx` | JWT | Выгрузка разбора в `.docx` |

`ContestKind` — `Individual` (по умолчанию), `University`, `Nonprofit`. От него зависит, какие
критерии оценки агент поднимает из методички: у конкурсов для физлиц, вузов и НКО они разные.

Выгрузка разбора — сухой документ: заголовок, дата и содержание. Ни бланка с исходящим номером, ни
блока подписи с должностью и строкой исполнителя там нет: это результат автоматической проверки,
а не письмо за подписью, и оформлять его как официальный документ вводило бы в заблуждение.

### Файлы

| Метод | Путь | Доступ | Описание |
|---|---|---|---|
| `GET` | `/api/documents?kind=&limit=50&offset=0` | `Rector`, `Coordinator` | Реестр со статусом разбора по всем пользователям |
| `GET` | `/api/documents/{documentId}/content` | владелец или staff | Скачать файл |
| `DELETE` | `/api/documents/{documentId}` | владелец или staff | Удалить файл из хранилища и реестра |
| `GET` | `/api/reviews/active` | владелец | Разборы, идущие прямо сейчас: для восстановления статуса после перезагрузки |

Реестр и скачивание разделены намеренно. **Реестр** — служебный, он показывает чужие заявки
с персданными и закрыт от заявителей целиком. **Скачивание** — по владельцу: свою заявку
пользователь качает из чата, чужую не получит (`PermissionDenied` в `DocumentService.DownloadAsync`).

`kind` — `Manual`, `GrantApplication`, `GeneratedDocument`.

**Удаление** идёт по владельцу так же, как скачивание, и чистит всё, что тянется за файлом: объект
в S3, запись в реестре, а для заявки — ещё и сохранённый разбор с критериями. Файл методички
удаляется вместе с самой методичкой: её разделы и эмбеддинги без исходника не нужны, проверять
по ней заявки уже нельзя.

Пока по файлу идёт работа — заявка в разборе, методичка в стадии `Queued`/`Parsing` — удаление
отклоняется с `400`, иначе воркер оборвался бы на середине. Сообщения чата со ссылкой на удалённую
заявку остаются, но скачать по ним уже нечего; об этом предупреждает подтверждение в UI.

### Поручения

| Метод | Путь | Доступ | Описание |
|---|---|---|---|
| `GET` | `/api/assignments?status=&limit=50&offset=0` | `Rector`, `Coordinator` | Список по всем |
| `GET` | `/api/assignments/{assignmentId}` | `Rector`, `Coordinator` | Одно поручение |

### SignalR — `/chat-hub?ticket={guid}`

| Метод хаба | Описание |
|---|---|
| `CreateChat` | Создать чат |
| `GetChatList(lastChatId, limit)` | Список чатов |
| `GetMessages(chatId, lastMessageId, limit)` | История сообщений |
| `SendMessageToConsultingAgent(chatId, content, manualId)` | Сообщение консультанту |

`GetMessages` возвращает у каждого сообщения необязательный блок `file` (`documentId`, `fileName`,
`reviewMessageId`) — из него фронт рисует виджет вложения. Поэтому вложение переживает
перезагрузку: оно часть сообщения, а не состояние страницы.

Клиентские события:

| Событие | Полезная нагрузка |
|---|---|
| `AiStatusUpdate` | `chatId`, `status` — прогресс агента |
| `FileStatusChanged` | `fileName`, `status` (`Queued` / `Reviewing` / `Reviewed` / `Failed`) |
| `ReviewReady` | `chatId`, `documentId`, `messageId`, `content` |
| `ReviewFailed` | `chatId`, `fileName`, `messageId`, `reason` |
| `ManualStatus` | `manualId`, `title`, `stage` (`Queued` / `Parsing` / `Ready` / `Partial` / `Failed`), `totalChunks`, `processedChunks`, `failedChunks`, `detail`, `gaps` |

`chatId` в `AiStatusUpdate` и `documentId` в `ReviewReady` нужны для адресации: события летят
в группу пользователя, а не чата. Без них статус показывался бы в любом открытом чате, а кнопку
«Разбор» некуда было бы привязать при нескольких заявках в одном чате.

### Две схемы аутентификации

REST работает на обычном JWT Bearer. SignalR заголовки отправить не может, поэтому у хаба своя схема
`WebSocketScheme`: клиент с JWT дёргает `GET /api/auth/ws-ticket`, получает одноразовый тикет с TTL
30 секунд и подключается на `/chat-hub?ticket={guid}`. Каждое соединение вступает в группу
`user:{userId}` — туда и приходят статусы агента и готовые разборы, в том числе от фонового воркера.

### Ошибки

Все доменные исключения приводятся к `ProblemDetails` в `DomainExceptionHandler`:

| Код | Когда |
|---|---|
| `400` | Битый документ или неверный запрос |
| `403` | Отказ в доступе |
| `404` | Не найдено |
| `429` | Лимит GigaChat |
| `502` | Прочие отказы GigaChat |
| `503` | Анонимайзер недоступен |

Фронт достаёт из ответа `errors`, `detail` или `title` — в таком порядке.

## Грабли

**Valkey нужен с модулем поиска.** Обычный `redis:alpine` или `valkey/valkey` не подойдут — код
использует `FT.CREATE`/`FT.SEARCH`. В compose стоит `valkey/valkey-bundle`, где модуль уже есть.
Поэтому же у сервиса `valkey` намеренно не переопределён `command`: свой `valkey-server` без конфига
образа отключит загрузку модулей, и приложение упадёт на создании индексов.

**Смена модели эмбеддингов ломает индексы молча.** `ValkeyIndexInitializer` создаёт
`idx:manual_parts_v2` и `idx:pins` только если их нет. Если поменять `GIGACHAT_EMBEDDING_DIM`,
`FT.CREATE` просто не выполнится, а старая размерность останется. Нужно удалить индексы:

```powershell
docker compose exec valkey valkey-cli FT.DROPINDEX idx:manual_parts_v2
docker compose exec valkey valkey-cli FT.DROPINDEX idx:pins
docker compose restart chatnode
```

**Бакет создаётся отдельным контейнером.** SeaweedFS не создаёт бакет сам при первом `PUT`, поэтому
`seaweedfs-init` дожидается S3-порта и делает `PUT /{bucket}`. Если переименовали `S3_BUCKET` —
нужен повторный `docker compose up seaweedfs-init`.

**Порт `5064` торчит наружу на всех интерфейсах.** В отличие от `valkey`, `postgres`, `seaweedfs`
и `anonymizer`, привязанных к `127.0.0.1`, сервис `chatnode` публикуется без привязки к адресу.
Это прямой доступ к API в обход nginx с его `client_max_body_size`. Для публичного развёртывания
стоит либо привязать его к `127.0.0.1`, либо убрать проброс совсем и ходить только через `web`.

**`UseHttpsRedirection` включается только в Development.** HTTPS-порт не настроен, поэтому
в Development в логах будет предупреждение `Failed to determine the https port for redirect`.
Запросы при этом проходят; TLS терминируйте на внешнем прокси.

**Ограничение — размер промпта, а не качество модели.** Русский текст стоит GigaChat примерно один
токен на 3 символа, и в каждый запрос уезжает системный промпт плюс полная JSON-схема всех
инструментов — причём заново на каждом витке цикла вызовов, тогда как текст фрагмента отправляется
один раз. Окно забивают **накопленные результаты вызовов инструментов**, а не входной текст: каждый
вызов дописывает найденные части методички и находки обратно в тот же диалог. Поэтому при `413`
уменьшать входной фрагмент обычно бесполезно — сначала посчитайте, сколько возвращают инструменты.

Диагностика по логам: если в них появились записи `не влез -> урезаю вызовы инструментов`, снижайте
`GIGACHAT_SECTION_TOOL_CALLS`, а если и это не помогло — `GIGACHAT_SECTION_CHARS` до 3000.
Записи вида `Методичка …: поиск "…" -> N частей, M симв.` печатают суммарный размер выдачи поиска
по методичке — это самая дорогая позиция в цикле, и при разборе `413` смотреть надо в первую очередь
на неё. Обе видны при `LOG_LEVEL_AGENT=Debug`, который стоит по умолчанию.

**Данные в Valkey живут сутки.** Чаты, сообщения и находки истекают по `EXPIRATION_*`. Разборы,
методички, поручения и учётки лежат в PostgreSQL и не истекают. Если чат исчез, а разбор остался
в разделе «Файлы» — это ожидаемое поведение, а не потеря данных.
